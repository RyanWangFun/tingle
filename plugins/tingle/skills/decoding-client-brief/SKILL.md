# decoding-client-brief

## 概述

一句话职责：**把一份客户 brief 拆成一份团队明天能动手的方案框架，并交代它凭什么这么拆。**

- **拆解占八成，抄作业占两成**：产出质量几乎全部取决于目标定得准不准、真问题验没验过；找对标只是最后那两成。
- **本环节唯一的交付物是方案框架**。目标解读、KPI 读穿、真问题界定、对标池、体检结论，都是支撑它的判断，不单独交付、也不许缺。
- **客户说的问题往往不是要解决的那个问题**。照着 brief 的字面做方案，是这个环节最贵的一种失败——它不会当场暴露，会等到一整轮跑完才暴露。

## 何时用 / 何时不用

**何时用**：新客户或新产品的 brief 到手；客户给了一个目标或 KPI 需要拆成可执行方案；客户拿一个表象、一个别人的案例或一个"问题"过来要你照做。

**何时不用**：
- 要定我方对外承诺的 KPI 数值、要准备跟客户谈判的依据——那是另一个环节，本环节只**读懂客户给的那个数**，不产我方承诺。
- 要做人群、需求、内容、投放、搜索承接、卖货、复盘中任一件——各归各的环节，本环节不代做。
- 手上没有 brief、只有一堆散材料——那是材料蒸馏的活，REQUIRED BACKGROUND: `tingle:context-distill`。

## 运行前

**第一步跑 `tingle check decoding-client-brief`**，拿到开工单再开工；拿到卡点单本次不跑，按卡点单载入 REQUIRED SUB-SKILL: `tingle:project-readiness` 修完复验。开工单上附着的就绪判据由本 skill 开跑时逐条对照判，判不准停下问人，不许挑一个解释混过去。

## 业务方法

五道工序按序走。**每道工序的细节在它自己的深读件里，走到那一道再读那一份**——主手册只装每次都要遵的东西：这道工序要产出什么、不许怎么做。

| 工序 | 产出什么 | 走到这一步读哪份 |
|---|---|---|
| 一 · 定目标 | 预期类型、品牌阶段、可用工具范围、认知病灶清单 | `references/reading-the-client.md` |
| 二 · 读穿 KPI | 目标类型、绝对数字、决策成本档、链路终点与监测、是否撞人群上限 | `references/kpi-translation.md` |
| 三 · 验真问题 | 真伪判定、真问题一句话、根因落点、解决方向 | REQUIRED BACKGROUND: `tingle:validating-the-real-problem` |
| 四 · 建对标池并算账 | 进池品牌 + 各自三信号判定 + 论证后的投入产出 | `references/competitor-benchmarking.md` |
| 五 · 体检并落成方案框架 | 四条体检结论 + 方案框架六格 | `references/business-health-check.md` |

### 工序一 · 先定目标，再配工具

**禁止**：

- **禁止照着客户写的做法往下拆。** 客户写"找一批人做测评"是做法不是目标；先往前推一步问"做这件事到底想干嘛"。目标判错，后面每一步都在为错的目标服务，且步步自洽、无人察觉。
- **禁止让"既要又要还要"活着进下一步。** 同一阶段不可能什么都要；目标不同，对标竞品就不同、打法就不同。brief 里并列出现多个诉求的，回去让客户排序；排不出的列入待确认项，**不许自己挑一个当主目标接着拆**。
- **禁止用一类预期的尺子量另一类预期。** 营销项与效果项的衡量方式完全不同，拿投入产出比去卡一个只要曝光美誉度的客户，或拿曝光交差给一个要成交的客户，都是这一刀没切干净。

**本工序不产出那四个结论就不许进下一道工序。** 任何一个含混，回去追问客户。

### 工序二 · 把 KPI 读穿成可倒推的数字

**禁止**：

- **禁止让一个模糊词活着进下一步。** "数据好""转化高"必须先换算成可衡量形态；换算不了的列入待确认项，**不许填一个像样的数进去**——下游会当真值用。
- **禁止在没判决策成本档之前拆 KPI。** 同一个销售额目标，高低两档的拆法、卡位要求、发言身份要求完全两套，漏判等于没拆。
- **禁止漏判链路终点。** 结果最终落在哪一段，决定整套衡量与监测方式；判不出来，方案框架里的每个数字都无处可挂。
- **禁止套用别的品类的回传比例、转化率、点击率当本品类的取值。** 每一个数都要标来源，取不到就标"未披露"。

### 工序三 · 验真问题

**凡客户给的是问题型诉求，或拿一个表象让你照做，一律先走这一道，不许跳。**

**这一道的方法本身不在本 skill 里**——它横切多个环节（读 brief 与复盘用的是同一套），按 REQUIRED BACKGROUND: `tingle:validating-the-real-problem` 执行。本 skill 只守两条与 brief 场景相关的纪律：

- **禁止把这一道跳过去。** brief 里但凡出现"转化率低""数据不好""加了预算营收不变"这类问题型表述，或者出现一个别人的案例要你照做，**都要先验真再往下拆方案**——照着字面做方案是这个环节最贵的一种失败。
- **禁止把验真结果留在脑子里。** 它的三条结论（真伪、真问题一句话、根因落点）要落进本环节的产出，**方案框架的每一格都要能挂回那个真问题。**

**本工序的输出必须写成可判的形态**：真问题是一句含起点数与目标数的话；根因落到六个落点之一（流量／内容／人群／渠道／动作没做到位／玩法不适配）。

### 工序四 · 建对标池并算清它们的账

**禁止**：

- **禁止把成长阶段不匹配的品牌放进对标池。** 已建立稳固心智的头部，其合作率、预算、玩法与起盘者差一个数量级，看它只会带偏。
- **禁止只算水上不算水下。** 把公开的合作费用当成全部成本，会把对方的投入产出严重高估——这是对标失败的头号死因。
- **禁止用对方对外分享的口径当依据。** 对外说的数字常常是过去某个时点的，一律回收数据自行论证。

**三条纪律每次都守**：① **一定要论证**（回收数据自行验证）；② **一定要判可复制性**（这套打法至少对本方七成适用才值得抄）；③ **信息维度要足够多**（不止看一个竞品一种玩法，要往下挖它是否与自身产品特殊性、竞争激烈度、切入时点、团队结构强相关）。

### 工序五 · 体检盘子，落成方案框架

先过体检四问（结论没有问题的写"无"，不许留空），再落方案框架。**方案框架至少六格，每格都要能指认它出自 brief 原文哪一句、或哪份材料的哪一条**：

| 格 | 装什么 |
|---|---|
| 对标竞品 | 进池的品牌 + 各自论证后的投入产出 |
| 整体玩法 | 该走哪一档 + 与本方团队基因的匹配度 |
| 内容线 | 优先方向、最大曝光点、多样性怎么保证 |
| 身份线 | 要什么类型的发言身份、破圈方向 |
| 预算与费用结构 | 内容费、广告费、测试期先花多少建数据基点 |
| 月度执行表 | 每月做多少互动 → 多少条什么形态的内容 → 需要什么类型的人来做 |

**禁止把任何示例阈值写成本项目的基准线。** 多少搜索量算起盘、点击率多少算能跑、投入产出比多少算达标——这些随品类、客单价、内容形态而变，一律用本方历史数据或本次回收的数据重建；没有就写"需先建监控，当前无法给确定值"。

## 接口与边界（声明）

- **适用环节**：「把一份客户 brief 拆成方案框架」——换一个客户项目也会再次发生的固定环节，非一次性事务。
- **input schema**：`brief原文`（客户一手文本，字符串）；`产品事实`（品类、客单价、规格、决策成本，对象）；`客户目标原话`（字符串）；`已知约束`（预算、时间窗口、合规、渠道限制，字符串数组）；`客户历史数据`（可选，对象；无则按未披露处理）。
- **output schema**：`目标解读`（预期类型、品牌阶段、可用工具范围、认知病灶清单）；`KPI读解`（目标类型、绝对数字形态、决策成本档、链路终点类型与监测方式、是否撞人群上限）；`真问题界定`（真伪、真问题一句话、根因落点、解决方向）；`对标池`（每个品牌含三信号判定与论证后的投入产出）；`体检结论`（四问各一条）；`方案框架`（六格）；`待确认项`（数组）；`未披露项`（数组）。**可沉淀候选（reusable_candidates）**：`对标池`（同品类下一单还用得上）、`真问题界定`里那条"问题 → 根因"的判断路径、`KPI读解`里回收到的数据基点（互动与搜索的换算关系、单位成本、转化率量级）。——**它们只是候选；够不够格真的留下、沉进哪一格、标什么成色，按 REQUIRED BACKGROUND: `tingle:banking-proven-assets` 判。**
- **写回位置**：`方案框架落点`（见 requirements 的 outputs 段），地址由项目档案登记，不自行选址。
- **规则层与项目事实**：运行时挂 **合规类目层** 与 **品牌层**（判方案框架里的表述与承诺能不能给、品牌既有心智是什么）；不挂类型层与通用层——本环节不产对外内容。所需项目事实字段：`合规类目`、`产品品类`、`品牌`、`阶段`。
- **工具**：读飞书文档与多维表格（经开工单地址取得）、写飞书文档（登记的落点）。无其它外部接口调用。
- **决策档**：**复核**——本环节对项目走向本身做判断（真问题是什么、该走哪档打法、盘子成不成立），产出须有人过目才算数，不得自动放行。
- **复核包**：方案框架本体 ＋ 每格的原文出处（引到 brief 原句或某份材料某条）＋ 真问题验真的数据化过程（把哪个模糊词换算成了什么数、据什么判真伪）＋ 对标池每个品牌的三信号逐条判定 ＋ 未披露项清单 ＋ 待确认项清单。
- **升级条件（命中即停交人）**：①方案框架里任何写给客户看的表述触及合规红线而判据不确定；②四层规则冲突（两层各有一套说法）；③缺关键项目事实（合规类目、产品品类、阶段任一取不到）；④产出需对外发送（交给客户、进提案）；⑤判定客户提的是伪问题、真问题另有其一；⑥对标池定稿；⑦体检判出"盘子不成立"或"需要结构升级"；⑧brief 里并列多个目标且客户未排序。

## 产出验收判据（DoD）

一次运行合格，当且仅当：

1. 方案框架六格全部填了，且每格能指认它出自 brief 原文哪一句、或哪份输入材料的哪一条；
2. 客户给的每个目标或诉求都归到了三类目标之一，并换算成绝对数字；换算不了的已列入待确认项，**没有一个模糊词被当作数字用**；
3. 产出全文出现的每个数字都标了来源（brief 原文／某份材料某条／竞品回收／未披露）；原材料没有的一律标"未披露"，全文无推断值冒充实测值；
4. 已判定客户提的问题是真是伪；判为伪的，真问题写成一句含起点数与目标数的可衡量的话，并写明根因落在六个落点中的哪一个；
5. 对标池里每个品牌都逐条过了三信号并留下判定，任一信号不过的不在池内；
6. 体检四问各有一条结论（无问题的写"无"），不留空；
7. 方案框架里每个数字承诺都挂得回一段定性意图——按 REQUIRED BACKGROUND: `tingle:keeping-metrics-anchored` 判，有孤儿指标或裸承诺即不合格；
8. 待确认项与未披露项两份清单随产出交出，**不许因为清单空着好看就把不确定的项填掉**。

## Quick Reference

| 情形 | 动作 |
|---|---|
| brief 写的是做法不是目标 | 往前推一步问"做这件事想干嘛"，把做法降级为备选手段 |
| brief 并列多个诉求 | 回去让客户排序；排不出即列待确认项、停 |
| 客户只说"想要转化" | 归入流量需求类，按 `搜索量 × 转化率 × 客单价` 倒推 |
| 客户给的是增长率 | 先换算成绝对数字再往下拆 |
| 客户说"数据不好" | 先数据化（从多少变成多少、连续多久），再判真伪 |
| 高决策成本品类 | 卡位与发言身份要求另一套，且不许用爆文数考核 |
| 加了预算营收不变 | 查是否撞人群上限；撞了走"往前推"或"换品复用" |
| 想拿一个头部品牌当对标 | 先过三信号；阶段不匹配即出池 |
| 对方对外说投入产出很高 | 回收数据自行论证，不采信对外口径 |
| 客户要求照抄某套玩法 | 拆成要素逐条对照本方，不具备就变形成可行的样子 |
| 手上没有本品类的基准线 | 写"需先建监控，当前无法给确定值"，不借用别的品类的值 |

## Common Mistakes

- **照着 brief 的字面往下拆**——最贵的一种错：整份方案自洽地服务于一个伪问题，跑完一轮才暴露。
- **把模糊诉求填成一个像样的数**——"提升认知""促进转化"等于没写；下游会把它当真值用。
- **判了目标类型却没判决策成本档**——同一个销售额目标，两档的拆法完全不同。
- **对标池里放了一个已建立稳固心智的头部**——它的每一项条件都和起盘者差一个数量级。
- **只算对方的公开合作费用**——漏掉水下投入，投入产出被严重高估。
- **把某个示例阈值当通用真值**——阈值随品类、内容形态、自身历史而变，必须重建。
- **体检四问留空**——留空与"体检过了没问题"在文本上分不开，没问题也要写"无"。
- **待确认项清单空着交出去**——不确定的项被填掉了，而填掉的那一刻没人知道。
- **该读深读件的工序凭印象做**——四份深读件各对一道工序（验真问题那一道走方法技能），走到哪一道读哪一份，不读就做等于跳过判据。

## Red Flags（出现即停，回到对应工序）

- 「客户就是这么要求的，照做就行」→ 回工序一，先定目标。
- 「几个目标都挺重要，一起做吧」→ 回工序一，排序或停。
- 「这个数大概是这个量级，先填上」→ 回工序二，标未披露。
- 「问题很明显啊，不用验了」→ 回工序三，先数据化。
- 「这个头部品牌做得好，就抄它」→ 回工序四，过三信号。
- 「他们对外说投入产出有那么高」→ 回工序四，回收论证。
- 「基准线照这个数写就行」→ 回工序五，用本方历史或本次回收重建。
