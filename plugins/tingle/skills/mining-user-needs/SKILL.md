# mining-user-needs

## 概述

一句话职责：**把每类人身上的真需求挖出来，并翻译成他自己会说的那句话。**

- **内容做的是解决方案，不是产品**。用户在这里的路径是发现内容先于发现商品，他找的不是产品，是能解决他问题的那个东西。
- **挖掘与表达是两件事，本环节只负责挖掘**。挖准了痛在哪，才谈得上怎么表达；挖错了，表达再花也是戳空气。
- **两条路必须都走**：从产品端推（保证不漏自家卖点），从已跑出结果的素材端反向抽（保证抓到市场已验证的真需求）。只走一条都会漏。

## 何时用 / 何时不用

**何时用**：人群表已定，要把每个人群的需求挖到能写内容的颗粒度；内容发了很多但没人来搜、要回头查需求；抄了对方的爆款却没结果、要找那个"绝对影响因素"。

**何时不用**：
- 要定人群本身——那是上游环节，本环节吃它的产出。
- 要把需求写成具体的内容角度、写成成片、配投放、做复盘——各归各的环节。**本环节到"这个人要解决什么、他自己会怎么说"为止，不碰画面、话术、体裁。**

## 运行前

**第一步跑 `tingle check mining-user-needs`**，拿到开工单再开工；拿到卡点单本次不跑，按卡点单载入 REQUIRED SUB-SKILL: `tingle:project-readiness` 修完复验。开工单上附着的就绪判据由本 skill 开跑时逐条对照判，判不准停下问人。

## 业务方法

四道工序。**一、二必跑；三对每条需求都要跑；四在"要抓市场已验证的真需求"或"抄了没结果要查真因"时跑。**

| 工序 | 产出需求表的哪几列 | 读哪份 |
|---|---|---|
| 一 · 把卖点翻译成买点 | 用户语言表述、导向 | `references/selling-point-to-buying-point.md` |
| 二 · 从人群裂变出需求与痛点 | 需求／痛点、来自哪条特性、搜索池／曝光池 | `references/mining-needs-from-audiences.md` |
| 三 · 打分与排序 | 痛点维度、离痛点近度、市场需求量 | `references/pain-proximity.md` |
| 四 · 从已跑出结果的素材反向抽 | 需求原话、位置、频率 | `references/needs-from-top-performers.md` |

### 工序一 · 把卖点翻译成买点

**天平的两端**：一端是产品与商家（我们的卖点＝产品特性），一端是用户（他的需求与他的语言）。**做不好的根因只有一个：习惯把重心压在自己这端，自嗨讲"我产品多厉害"。**

**禁止**：

- **禁止用产品词或专业词描述需求。** 用户脑子里没有那个词，看到只会觉得跟自己无关。要换成他自己会说的处境话。
- **禁止给非自用人群写内在感受词。** 购买者感知不到使用者的内在感受，只能感知第三方可见的变化——要让他产生"好像和我家那位差不多"的代入。
- **禁止先定表现形式再找关键词。** 顺序是**先关键词、后表现形式**：用户不会搜"自用分享""好物推荐"，他搜的是自己的处境。
- **禁止直接把功效词写成买点。** 功效是卖点的换句话说；买点是"谁、在什么场景、因为什么问题需要它"。

**做法**：先客观拆产品特性（不带任何用户语言）→ 对每条特性做"哪些人、什么场景、什么需求"的填空 → 把人和需求转译成用户会说的关键词。**每多一个新买点，就多一个新人群，就多一个新增量。**

### 工序二 · 从人群裂变出需求与痛点

**禁止**：

- **禁止跳过"产品能干什么"直接想内容。** 裂变路径是：产品 → 产品功能 → 这个功能能服务哪些人 → 这些人的需求与场景 → 用什么内容跟他们沟通。
- **禁止让抽象功能直接对人群。** 功能抽象时（如"抗菌""调理"），**先穷举症状与痛点，再由症状反推人群与场景**——症状会引发用户的警觉性，抽象功能不会。
- **禁止只挖到"表面痛点"。** 用户说的那个问题背后往往还有一个**绝对影响因素**；同样打一个痛点，有人效率高有人低，区别就在有没有挖到那一层。
- **禁止只押一个流量端口。** 每条需求都要二次拆进搜索池（用户脑子里已有、会主动搜的词）和曝光池（用户没在搜、但被场景痛点击中）两个端口。

### 工序三 · 打分与排序

**买点列出来往往有很多个，人力预算有限不可能全做，必须排优先级。**

**三近原则**（同时看三项）：离用户痛点更近（戳中迫切要解决的刚性问题）、离用户决策更近（接近他做购买决策的那一刻）、离用户现状更近（贴合他当下的具体处境）。

**禁止**：

- **禁止把需求量当唯一排序依据。** 顺序是：先找同时满足三近的方向，再用数据判断当下市场需求量，再按需求量从高到低把资源压上去。
- **禁止做需求量太窄的方向。** 再努力也拿不到多少流量——**该砍就砍**。
- **禁止在没有工具读数时填一个需求量。** 未验证的一律标"待验证"并写明需用什么工具验证哪个字段。

**痛点三维度**：痛点（迫切要解决的刚性问题）／痒点（尚未明确表达的潜在需求，要用内容先唤醒）／爽点（超出预期的即时满足）。**当痛点维度做到流量天花板时，往痒点推**。

### 工序四 · 从已跑出结果的素材反向抽需求

**这一道解决的是"从产品端推出来的需求，市场到底认不认"。**

**禁止**：

- **禁止把需求抽象掉。** 记录一律用**原话**——素材里说"运动出汗一整天不脱妆"，就记这句，不许抽象成"户外场景需求"。抽象掉的不只是颗粒度，是下一次能直接拿来用的那句话。
- **禁止不带人群看需求。** 一条需求你自己不会买，不代表它没需求，只代表你不是它的人群。
- **禁止用"我早就知道"代替做一遍专项。** 知道某个痛点是核心，和把二十条对标拆完、看到它在榜单里的位置与出现次数，是两种认知质量。

**做法**：取一批对标素材 → **只看开头几秒、只看需求**，别的一概不看 → 输出需求词单 → 每条标两个统计维度：**位置**（它所在素材在榜单里的排名，越靠前对应消耗越大）与**频率**（在这批里出现几次，**出现两次以上就重视**）。

## 接口与边界（声明）

- **适用环节**：「把人群转译成一张带用户语言与优先级的需求表」——换一个客户项目也会再次发生的固定环节，非一次性事务。
- **input schema**：`人群表`（数组，每行含人群、自用非自用、来自哪条特性、触达语言约束）；`产品特性`（数组，每条含特性与其作用机制）；`对标素材`（可选，数组；每条含素材内容与其在榜单中的排名）；`工具读数`（可选，对象；搜索量、内容量、互动量）。
- **output schema**：`需求表`（数组，每行含：人群、需求／痛点、用户语言表述、需求原话与位置与频率、痛点维度、离痛点近度、搜索池／曝光池、市场需求量与验证状态、来自哪条特性、表达约束备注）；`待验证清单`（数组）；`已砍方向及原因`（数组）；`绝对影响因素`（数组，写明每条需求背后被挖出的那一层真因）。**可沉淀候选（reusable_candidates）**：`需求表`里带原话与频率、且已被市场验证的需求条目（同品类下一单直接调用）、`绝对影响因素`（这类洞察跨单成立）、验证过的关键词衍生路径。——**它们只是候选；够不够格真的留下、沉进哪一格、标什么成色，按 REQUIRED BACKGROUND: `tingle:banking-proven-assets` 判。**
- **写回位置**：`需求表落点`（见 requirements 的 outputs 段），地址由项目档案登记，不自行选址。
- **规则层与项目事实**：运行时挂 **合规类目层**（判用户语言表述里的症状词、功效暗示能不能用——**要打某个功效，就要有相对应的资质**）与 **品类层**（痛点池与公共痛点随品类变）；不挂类型层。所需项目事实字段：`合规类目`、`产品品类`、`品牌`。
- **工具**：读飞书文档与多维表格（经开工单地址取得）、写飞书多维表格（登记的落点）。平台侧搜索量与素材榜单数据由人提供读数，本 skill 不直接调用平台接口。
- **决策档**：**复核**——需求表是内容方向与成片的直接依据，挖错了下游全跑偏，产出须有人过目才算数。
- **复核包**：需求表本体 ＋ 每条需求"来自哪条特性或哪个人群"的回溯 ＋ 每条用户语言表述的来源（用户原话出处或素材出处）＋ 需求量数据的来源与采集时间 ＋ 待验证清单 ＋ 已砍方向及原因 ＋ 挖出的绝对影响因素及其依据。
- **升级条件（命中即停交人）**：①用户语言表述触及合规红线而判据不确定（尤其是把症状或功效说到需要资质才能说的程度）；②四层规则冲突；③缺关键项目事实（合规类目、产品品类任一取不到）；④输出需对外发送；⑤要砍掉某个方向；⑥判定某条需求背后另有绝对影响因素、并据此改写需求；⑦拿不到任何需求量读数、全部无法验证。

## 产出验收判据（DoD）

一次运行合格，当且仅当：

1. 需求表每一行都能指认它**来自哪个人群、哪条产品特性**；指认不出的行不在表内；
2. 每一行的"用户语言表述"里**不含任何产品词、专业词或内部术语**；标非自用的人群那几行，表述里不含内在感受词；
3. 每一行都标了搜索池或曝光池，**没有一行两个端口都空着**；
4. 每一行都打了离痛点近度，且写明它由三近的哪几项推出来；
5. 市场需求量取自真实工具读数并标了来源与采集时间；取不到的标"待验证"并写明需用什么工具验证哪个字段，**没有一个数是臆造的**；
6. 从素材反向抽出的需求条目，**记的是原话**，且各自带位置与频率；出现两次以上的条目已被标为重点；
7. 被砍掉的方向都写明了原因（需求量太窄／三近不过／红线不过），**不是无声消失**；
8. 需求表里出现的每一个量化字段都挂得回一个定性意图——按 REQUIRED BACKGROUND: `tingle:keeping-metrics-anchored` 判，有孤儿指标即不合格。

## Quick Reference

| 情形 | 动作 |
|---|---|
| 产品特性很抽象 | 先穷举症状，再由症状反推人群场景 |
| 需求写出来像功效词 | 没转译完——继续问"谁、什么场景、因为什么问题" |
| 买的人不是用的人 | 用第三方可见的现象 + 代入感，不用内在感受词 |
| 买点列了很多做不完 | 先过三近，再按需求量排，把资源压到最大的那个 |
| 痛点方向做到流量天花板 | 往痒点推，用内容唤醒尚未表达的需求 |
| 抄了对方爆款没结果 | 挖它背后的绝对影响因素；看它的购买对象是不是你的人 |
| 要快速知道市场认哪些需求 | 取一批对标只看开头、只看需求，统计位置与频率 |
| 记录需求时想概括一下 | 停——记原话，抽象了下一单就用不了 |
| 需求量查不到 | 标待验证，写明用什么工具验哪个字段 |
| 要提某个功效 | 先查有没有相对应的资质，没有就换表述 |

## Common Mistakes

- **站在商家视角写需求**——天平压在自己这端，用户没感知。
- **把功效词当买点**——功效是卖点的换句话说，不是买点。
- **抽象掉用户原话**——丢的是下一次能直接用的那句话。
- **只从产品端推需求**——漏掉市场已经验证跑通的那些真需求。
- **只看素材端不看产品端**——漏掉自家真正的卖点。
- **只挖到用户说出口的那层**——真正驱动购买的往往是它背后那个原因。
- **不带人群判断需求**——"我不会买"不等于"没需求"。
- **用"我早就知道"代替做专项**——知道和看到数据是两种认知质量。
- **只做搜索池或只做曝光池**——平台会动态平衡，押单一端口会被切。
- **需求量拍一个数**——一个编出来的数会一路当真值用到投放。

## Red Flags（出现即停，回到对应工序）

- 「这个卖点很强，直接写上去」→ 回工序一，做完填空再写。
- 「用户应该能懂这个词」→ 回工序一，换成他自己会说的话。
- 「抗菌就是给有炎症的人用」→ 回工序二，先穷举症状。
- 「他说的就是他的痛点」→ 回工序二，往下挖绝对影响因素。
- 「这几个方向都做，别浪费」→ 回工序三，过三近再排序。
- 「把这几条需求归纳一下更清楚」→ 回工序四，记原话。
