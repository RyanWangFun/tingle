# 通用 Skill 构建标准

> 本件随 `tingle:building-work-skill` 一起分发，是它的判据参考件：那个 skill 管「下笔之前怎么想」，本件管「写完之后判得过判不过」。手上有一份 SKILL.md 就能用，不必另外找第二份文件。

---

## 概述与核心原则

本标准是「一个 Skill 是否合格」的判据集。判定对象＝一个 `.claude/skills/*/SKILL.md`（含 frontmatter 与正文）及其输入输出规格。

**核心原则**：Skill＝纯能力，无身份、无权限、不写死品牌／项目事实；每条判据是 PASS/FAIL 句或可判句，无裸形容词，读者只凭本条与一个 SKILL.md 即可字面判定。凡"复核／写回／升级"，本标准只判 SKILL.md 该**声明**什么，不判 Agent 侧如何路由。

条目分两块、各自独立成节：**① 可判定项**（机械可查，共 20 条）与 **② 不可约判断项**（需评审判断、仍写成可判句，共 3 条）。总计 23 条＝A 架构合规 12 条＋B 文件写法 11 条。

## 术语说明（判定句里用到的几个词，先看这一段）

判定句里有八个词是本标准的特定说法。每个一句话说清；说清之后 23 条全部自判得动，不必再去找别的文件。

- **规则层（通用・品类・品牌・类型 四层）**：一个 skill 运行时要遵的内容规则不写死在 skill 里，而是分四层存放、按当次任务装配上去——最宽的一层对谁都适用，往下依次是某一类业务共用的、某一个品牌自己的、以及某一种产出类型专有的（A8 判定句里说的"四层"就是这四层）。
- **决策档（自动／复核／决策）**：给一个 skill 的产出标一个"这东西能不能它自己说了算"的档位——自动＝出完直接用；复核＝出完须有人过目才算数；决策＝这件事本身要由人来定，skill 只负责把料备齐。
- **复核包**：交人复核时随产出一起附上的那套材料，作用是让复核的人不必回头翻上下文就能判这一次产出行不行。
- **升级条件**：一份写明"碰上哪几种情况就必须停下来交人、不许自己接着往下跑"的清单。
- **可沉淀候选（reusable_candidates）**：产出里那些"下一次别的任务还用得上、值得存下来复用"的字段，在输出结构里被单独标出来。
- **写回位置**：产出做完往哪儿存——由 skill 事先声明的落点字段，而不是每次由跑它的人临时挑个地方。
- **知识层**：存放那些会变、又不属于任何单个 skill 的规则内容本身的地方（违禁词表、创作原则、审稿判据、品牌红线一类）；skill 只声明运行时装哪一层，不把这些条目抄进自己正文。
- **Agent 层**：比单个 skill 高一层的运行环境，管的是人事与留痕——谁对哪一步负责、谁复核谁终裁、怎么鉴权隔离、留什么审计日志、由什么事件触发、多个能力之间怎么编排。

## 何时用 / 何时不用

**何时用**：
- 建或改一个 skill 前后，作者拿本标准逐条自检——建之前对照条目设计，交付之前逐条跑 PASS/FAIL。
- 审这个 skill 的人拿本标准逐条核，放行前过一遍。

**何时不用**：
- 微调走轻量路径的琐碎改动——判定见 §④ 琐碎豁免，不必全套。
- 非 `.claude/skills/*/SKILL.md` 的产物——本标准只判 Skill 一层，不判 Agent 责任编排、隔离矩阵、知识层归层。

## ① 可判定项（机械可查，读者拿一个 SKILL.md 即可字面判 PASS/FAIL）

### A 架构合规

**A2 · 适用性对应可重复环节**
判定句：SKILL.md 声明其适用工作项，且该工作项是**换一个客户项目也会再次发生的固定环节**（跨项目复现）。未声明适用工作项，或声明的适用对象为一次性／临时事务（只在这一个项目、这一次成立，换个项目不会再发生），任一情形 FAIL。

**A3 · 零品牌／项目专属事实（管全文）**
判定句：SKILL.md 全文（含示例、默认值、注释）不含任何品牌名、客户机密或具体项目事实，品牌／项目差异一律以运行时注入的占位表述承载。出现任一品牌名、客户机密或具体项目事实即 FAIL。
另见 B4：A3 管 SKILL.md 全文（正文／示例／默认值／注释）；B4 只判 description 字段这一处的专名。两条分工不重叠，各判各的位。

**A4 · 声明具名 input／output schema**
判定句：SKILL.md 声明结构化 input schema 与 output schema，二者均以具名字段（字段名＋类型或含义）列出。缺 input schema、缺 output schema、或以自由文本替代具名字段结构，任一情形 FAIL。

**A5 · 声明依赖的规则层与项目事实**
判定句：SKILL.md 声明其运行时需装配的规则层（通用／品类／品牌／类型 四层中具体挂哪几层）及所需的项目事实字段。未声明所依赖的规则层即 FAIL。

**A6 · 声明依赖的工具／接口**
判定句：SKILL.md 列出其执行所需调用的工具／接口清单。未声明所依赖的工具／接口即 FAIL。（接口就绪度与未就绪时的人工兜底不在本标准范围。）

**A8 · 复核包＋升级条件**
判定句：SKILL.md 定义（a）复核包内容清单——交人复核时随产出附上的材料；及（b）必停交人的升级条件清单——至少覆盖"合规红线不确定／四层规则冲突／缺关键项目事实／输出需对外发送"四项。缺复核包定义，或升级条件清单未覆盖上述四项，任一情形 FAIL。

**A9 · 声明写回位置＋可沉淀候选**
判定句：SKILL.md 声明其产出的写回目标位置字段，并在 output schema 中标出哪些字段为可沉淀候选（reusable_candidates）。未声明写回位置，或 output schema 未标出可沉淀候选，任一情形 FAIL。

**A10 · 不内嵌知识层可变规则**
判定句：SKILL.md 正文不内嵌应由知识层运行时加载的可变规则实体内容——平台违禁词表条目、通用创作原则条款、通用审稿流程判据、品牌红线／调性条目；只可引用"运行时加载的对应层规则"（加载声明见 A5）。正文一旦出现上述任一类规则的实体条目即 FAIL。

**A11 · 层边界：不越到 Agent 层**
判定句：SKILL.md 正文只描述"如何完成这一件能力"（输入→步骤→输出→复核包→升级条件）。出现责任编排、鉴权／隔离矩阵、复核路由（指定复核人／终裁人）、Run Log／审计留痕、触发与生命周期、或跨能力 Agent 编排等内容即 FAIL。

> **平台类 skill 的适用说明**：A11 禁的是 SKILL.md 正文替**运行环境**规定人事与留痕——谁对哪一步负责、谁复核、谁终裁、怎么鉴权隔离、留什么审计日志、由什么事件触发本 skill、指挥另一个能力何时运行。当一个 skill 的能力本体**就是**调度、路由、或"带着人去造另一个 skill"时，正文里出现路由步骤或触发条件，未必是越层。**判别问句：把这一段拿掉，本 skill 还完成得了它那一句话的职责吗？** 完成不了＝它是能力本体，不判 FAIL；照样完成得了＝它是外挂在能力之上的编排，仍判 FAIL。
> **本说明单向使用**：它只用来救"字面命中禁项、但可能是能力本体"的段落，只能把 FAIL 救成 PASS，**不能反过来把原本 PASS 的判成 FAIL**。A11 判定句正面许可的内容（输入→步骤→输出→复核包→升级条件）不进这个问句。

> **同级文件的处置（指引，不参与 PASS／FAIL）**：本条判的是 SKILL.md 正文，够不到与它同级的其它文件。但一个 skill 是以**整个目录**分发的，目录里那些文件按内容各有归属：
> ① 承载运行时要加载的规则、模板、格式规范的（多在 `references/`）——与正文同一把尺子，A3 的零专名、A10 的知识层边界照样管到它。
> ② **为这一个 skill 单独声明展示名、默认提示词、是否允许被隐式触发一类的清单件**（典型即市场／代理侧的 agent 清单文件）——**不随 skill 进插件**，删掉或留在作者自己的自用副本里。理由：装进插件之后，分发与触发由插件层统一承担，每个 skill 各带一份触发声明要么不生效、要么与插件入口的触发模型各说一套。它带的信息若有用（例如那句 `short_description`），只能当作写 `description` 时的素材，不得原样留成文件。
> ③ 可执行脚本、样例、评测件、素材件——不归本条管，按"运行时要用到的每一样东西从哪来"逐样点名，判它是跨项目同一份（随包，算工具依赖）还是随项目变（不随包，声明为运行前输入）。

**A12 · 声明可判的产出验收判据（definition of done）**
判定句：SKILL.md 声明该能力"什么样的产出算合格"的验收判据，且写成可判句、非裸形容词。判据可将内容层面的具体对错交由运行时加载的对应层规则承载（其加载依 A5 声明），但判据本身须可据以判定某次产出合格与否。缺验收判据、或验收判据仅为裸形容词（仅"写得好／高质量／专业"），任一情形 FAIL。

### B 文件写法

**B1 · description 为触发式**
判定句：description 用第三人称书写，且首句以触发条件起（"Use when…"或等义的"何时用"陈述）。出现第一人称，或首句改述"该 skill 做什么"而非"何时用"，任一情形 FAIL。
面：description

**B2 · description 不摘要流程**
判定句：description 不含对该 skill 内部工作流程／步骤的概述——不出现有序动作序列、阶段名列举或"先…再…"式过程陈述。description 复述了正文任一步骤链或阶段即 FAIL。
面：description

**B3 · description 含可检索关键词且问题导向**
判定句：description 至少含 1 个该 skill 适用场景的具体检索关键词（症状词、同义词、或涉及的工具／文件类型名之一），且触发描述指向"问题类别"而非某语言／工具特有的表层症状。无任何可检索关键词，或用语言特有表层症状冒充通用触发（除非该 skill 本身即绑定该技术且已在触发词中显式声明），任一情形 FAIL。
面：description

**B4 · description 零客户／项目专名、触发通用（专管 description 位）**
判定句：description 及其触发词不含任何客户名、品牌名、项目名或单一业务实例；触发条件写成可跨实例复用的"问题／场景类别"；若 skill 确为某技术专属，须在触发词中显式声明该技术。description 出现任一客户／品牌／项目专名，或把单一业务实例当触发条件，任一情形 FAIL。
面：description
另见 A3：本条只判 description 字段一处；SKILL.md 其余全文的专名由 A3 判。

**B5 · name 命名规范**
判定句：name 字段仅由字母、数字、连字符组成（无括号、空格、其它特殊字符，匹配 `^[A-Za-z0-9-]+$`），且首词为动词或动名词（-ing），按"做什么或核心洞察"命名。含括号／空格／特殊字符，或为被动名词化的模糊命名（如 "helper"、"utils"），任一情形 FAIL。
面：命名
> 决定：**不放宽——skill 一律 ASCII 短横名**，遵 writing-skills 原版、无中文名例外。

**B6 · 参考指南式章节结构、非叙事**
判定句：正文按参考指南组织，Overview（1–2 句核心原则）、When to Use（含 When NOT to use）、Quick Reference（表或可扫描清单）、Common Mistakes 四个核心小节均可在正文标题中逐一定位；且正文不含"某次会话我如何解决某问题"的一次性叙事段。缺四个核心节任一（极简纯 reference skill 缺 Common Mistakes 且已注明豁免理由的除外），或以一次性故事叙述代替可复用条目，任一情形 FAIL。
面：结构

**B7 · flowchart 克制使用**
判定句：每个 flowchart 仅用于非显然决策点、可能过早停止的流程循环、或"A 与 B 何时用"的判断；参考信息用表／列表、代码用代码块、线性步骤用编号列表承载，均不用 flowchart。出现承载参考资料／代码／线性步骤的 flowchart，或 flowchart 标签无语义（如 step1、helper2），任一情形 FAIL。
面：结构

**B8 · 正文精简（防臃肿，不设硬字数 FAIL）**
判定句：SKILL.md 无下列臃肿行为——(a) 把重型参考资料（约 100+ 行的 API／语法／大表）内联进 SKILL.md 正文，而非拆到单独文件按需加载；(b) 整段复制交叉引用即可指向的内容（重复另一 skill 已有内容）；(c) 把工具的命令 flag／选项逐项罗列进正文，而非指向 `--help`。命中任一即 FAIL。
> 长度只作软提示、非 FAIL：writing-skills 给的是"目标词数"（getting-started <150、高频加载 <200、其余 <500 词，L217–220），原文用"aim for"而非硬闸。硬字数 FAIL 不合理——合适长度随 skill 类型变，真正的浪费是内联重型参考+重复而非字数本身；且中文写作的 skill 无统一字数硬线。正文明显偏长时（可用 `wc -m` 粗估）触发一次"能否拆分/精简"复核，不自动判 FAIL。
面：精简

**B10 · 交叉引用其它 skill 的写法**
判定句：引用其它 skill 时只写 skill 名并加显式必需标记（如 `REQUIRED SUB-SKILL:` / `REQUIRED BACKGROUND:`），不用 `@` 路径链接、不用无标记的 "See skills/…"。出现 `@` 链接引用，或引用无必需性标记以致无法判断是否强制加载，任一情形 FAIL。
面：结构（交叉引用）

**B11 · 测试纪律：交付前先撞一次**
判定句：每个 skill 交付前须留存 ≥1 个"撞坏样例"记录——一份故意违反该 skill 要点的坏 SKILL.md（或坏产出），并记录它被哪条判 FAIL。无坏样例记录，或坏样例未被任何条目抓住，任一情形 FAIL。
> 分级（对应 B9"形式匹配失败类型"）：**技术／参考类 skill**（生成内容、拉数等）——轻量版即可，一个判废样例证明有牙。**纪律／合规类 skill**（审稿红线、合规把关等"人明知规则却在压力下会违反"的）——须做 writing-skills 原版完整测试：3+ 组合压力场景（时间／沉没成本／权威／疲劳）＋无 skill 时 baseline 复现＋逐条封堵合理化，直到压不动。
面：测试纪律（writing-skills Iron Law"无 failing test 不建 skill"）

## ② 不可约判断项（需评审判断，仍写成可判句）

以下 3 条的判定核心是评审判断本身，无法只凭字面机械查。仍写成可判句，供评审据以定 PASS/FAIL。**能机械判的条目一律已归入 ①，本节只留这三条。**（A1、A7 属 A 架构类；B9 属 B 文件写法类。）

**A1 · 单一职责**
判定句：SKILL.md 的能力可用一个动词短语（一句话）说清其单一职责，且不覆盖第二个可各自成句、可各自独立命名的能力。一个 SKILL.md 同时承担两个可各自独立命名的能力（例：既生成文稿又审核文稿）判 FAIL。
需评审之处：判"两个能力是否可各自独立命名"依赖对能力语义的判断。

**A7 · 决策档标注（策略类不得标自动）**
判定句：SKILL.md 为其产出标注决策档，取值为"自动／复核／决策"之一。若该能力属策略类（策略类＝对项目走向本身做判断的能力：是否立项、真问题是什么、采取什么策略、定什么指标、花多少预算），其决策档标注为"自动"即 FAIL。
需评审之处：判"该能力是否属策略类"需按上一行括号里那个定义（对项目走向本身做判断的能力）做归类判断；归类既定，"策略类≠自动"即机械可判。

**B9 · 指导形式匹配失败类型**
判定句：skill 中每处行为指导的形式与其针对的基线失败类型匹配——(a) 压力下明知故犯漏守规则 → 禁止式＋合理化对照表＋red flags；(b) 照做但产出走形 → 正面配方／契约；(c) 漏掉必产元素 → 模板中的 REQUIRED 槽位；(d) 行为应随条件变 → 挂在可观测谓词上的 conditional。形式与失败类型错配（如对走形问题只堆 "don't X"、对条件行为用无条件规则加豁免句），或指导中含消解自身的 nuance／豁免从句，任一情形 FAIL。
需评审之处：判"某处指导针对的是哪类失败、形式是否错配"依赖对指导意图与形式的判断。
面：形式匹配

## ③ 先撞坏草稿

**方法**：造一份故意违反本标准的 SKILL.md（虚构一个"标题生成"能力，写死的品牌名用虚构的"泽塔牌"，全程不涉任何真实客户名），把 ①② 全 23 条对它跑一遍。植入 8 组真实毛病，逐一记录被哪条判 FAIL。**每组毛病都被某条具名条目抓住** → 本标准有牙；任一组无条目能抓 → 该条缺牙、须回流补条目再撞。

# 标题生成器

## 概述
本 skill 给种草笔记生成标题，并顺带审核标题是否触犯平台合规红线——生成与合规审核两件事都在这里做完，省得再开第二个 skill。当前服务于泽塔牌保湿精华 2026 年 618 大促投放，主打"熬夜救星"卖点，客单价 199 元。

## 适用环节
内容创作阶段的标题产出。

## 输入 / 输出
- 输入：product_selling_points（产品卖点，字符串数组）、target_audience（目标人群，字符串）。
- 输出：title_candidates（候选标题，字符串数组）、compliance_flags（每条是否合规，布尔数组）。

## 依赖规则层
运行时加载：品类层、品牌层。

## 依赖工具
飞书文档读写接口、飞书多维表格读写接口。

## 决策档
复核。

## 能力一：生成标题
套用以下爆款公式：数字型「N 个理由让你…」、痛点型「熬夜党必看…」、悬念型「原来…一直做错了」。

## 能力二：审核合规
生成后逐条比对下列违禁词表，命中即打回重写。

### 平台违禁词表（一律禁用）
- 绝对化用语：最、第一、顶级、国家级、世界级
- 医疗功效：治疗、抗炎、消炎、修复屏障
- 夸大承诺：一夜见效、永久、根治、100% 有效

### 通用创作原则（标题必守）
1. 标题必须含 1 个阿拉伯数字。
2. 标题必须点出 1 个用户痛点。
3. 标题字数不超过 20 字。
4. 标题不得以问号结尾。

## 复核与留痕
- 复核人：内容组组长。
- 路由：生成后自动推送到组长飞书，她审完点"通过"后方可发布。
- Run Log：每次生成在 run-log.csv 追加一行，记录时间戳、操作人、候选标题数。
- 终裁：组长与投放组意见不一致时，由内容总监拍板。

## ④ 琐碎豁免

判"一个 skill／一次改动是否琐碎、可走轻量路径"——按下列三条件逐条对照，**任一不满足即非琐碎、走全套**：

1. **单文件**：改动只落在这一个 SKILL.md，不牵动其它文件。
2. **等价改动 ≤15 行**：改动规模不超过约 15 行且不改变语义契约（措辞订正、错字、格式）。
3. **无下游消费 且 无对外影响**：没有别的 skill／Agent／流程消费它的输出，且产出不对外发送。

**补充**（对上述通用条件的本地叠加）：

- **单点小功能 skill 的微调走轻量**：仅涉及该 skill 内部的等价小改动，满足上述三条件，作者自检通过即可，不必逐条全套过闸。
- **凡拟随插件正式发布的 skill 一律走全套**：无论改动多小，一律逐条跑 ①② 全部条目、并按 B11 留判废样例。

判定示例：给一个陌生人任一 skill／改动，他照上表三条件加两条补充逐项打勾——三条件全满足且不属拟随插件正式发布的 skill → 琐碎、走轻量；任一条件不满足或属拟随插件正式发布的 skill → 非琐碎、走全套。

## Red Flags / 常见错误

- **一个 SKILL.md 塞两件能力**——生成又审核、诊断又归因。违 A1，拆成两个。
- **正文写死品牌名或客户事实**——把差异硬编码进程序而非运行时注入。违 A3。
- **description 复述"先…再…"的步骤链**——把正文流程摘进触发描述。违 B2。
- **description 出现客户／项目专名**——触发词绑死单一业务实例。违 B4。
- **正文粘贴违禁词表／创作原则条款**——把知识层可变规则实体嵌进程序。违 A10。
- **SKILL.md 里写复核人是谁、怎么路由、留 Run Log**——越到 Agent 层。违 A11。
- **验收判据写成"写得好／高质量"**——裸形容词无可判据。违 A12。
- **交付前没留一个判废样例**——没被任何条目抓过的 skill 未验。违 B11。
