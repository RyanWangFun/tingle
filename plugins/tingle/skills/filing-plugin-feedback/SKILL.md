# filing-plugin-feedback

## 概述

一句话职责：**插件自己出了毛病，把它记成一条别人能读懂的记录，并让维护者当场知道。**

这条通道存在的理由：插件装在很多人的机器上，**撞上问题的人和能修问题的人不是同一个**。撞上的人最省事的做法永远是绕过去——一绕过去，问题就再也传不到能修它的人手里，插件停在「发出去了」而长不大。**这个 skill 唯一要对抗的，就是那句「算了绕过去」。**

三条基座（记牢）：

- **不打断当前的活**。撞到问题的当下不岔出去。手上这件事干完、或者已经卡死走不下去了，才提「要不要记一条」。
- **AI 填得出的一格都不许问人**。插件版本、当时在跑哪个 skill、原始报错、在哪个项目里撞上——全都在这次会话里，自己去取。多问一句，就是把成本转嫁给一个已经被绊了一次的人。
- **不经使用者点头不写出去**。这条记录会署他的名、会占用维护者的注意力。把要写的东西整条摆出来、等一声「记」，才写。

## 何时用 / 何时不用

**何时用**（三类都收，同一张台账）：

| 类型 | 长什么样 |
|---|---|
| **插件毛病** | skill 说明前后矛盾 / 读不出该怎么办、命令跑不通或报错、装不上、就绪流程卡住、文档写的和实物对不上 |
| **质量反馈** | 某个 skill 判得不对、产出的东西不好用、它的判据放到真实场景里不合用 |
| **需求许愿** | 希望这个插件还能干什么、希望哪一步能省掉 |

**何时不用**：

- **客户项目本身的问题**——材料缺、客户改口、红线不清、某份资料找不到。判法见 Step 1。
- **与插件无关的临时状况**——网断了、飞书在维护、重启一下就好了。
- **同一个问题已经报过、且这次没有新信息**——先查，查法见「报之前先查一遍」。

## 五步（硬结构，逐步走，不跳步）

> **本件不跑项目就绪检查。** 别的 skill 开跑前先查一次前提齐不齐，本件不查——**插件坏掉的时候，恰恰是就绪最可能不通过的时候**：装不上、程序跑不动、项目还没建，全都是该报的问题，而它们每一个都会让就绪检查不通过。把报问题这条路架在就绪之后，等于「越是坏得厉害越报不上来」。本件唯一的运行前提是飞书授权有效；连这个都没有，就走「写不进去怎么办」交可粘文本。

**Step 1 · 判这是不是插件的问题**

一句话判法：**换个客户项目、换个人、换台机器，这件事还会再撞上吗？**

- 会 → 是插件的问题（说明没写清、程序有毛病、前置没交代），往下走。
- 不会，只跟这个项目的材料或这一次的临时状况有关 → 不是本 skill 的活，就地结束，回去接着干原来的事。
- **判不准 → 当成是**，摆出来让使用者定。宁可多记一条，不可漏掉一个会反复绊人的坑。

**Step 2 · 定类型与严重度**（AI 自己定，不问人；摆给使用者时他可以改）

- 类型：插件毛病 / 质量反馈 / 需求许愿
- 严重度：**挡住干活**（没有绕法，这件事干不下去）/ **有绕法**（绕得过去，但每次都得绕）/ **不挡活**（小瑕疵、许愿）

**Step 3 · 把会话里已有的事实自己填满**（一格都不许问人）

| 要填的格 | 从哪儿取 |
|---|---|
| 出在哪 | 某个 skill / 插件程序 / 安装与就绪 / 文档说明 / 说不清 |
| 具体位置 | 当时在跑哪个 skill、敲的哪条命令、读的哪一段说明 |
| 复现线索 | 这次会话里做了什么才撞上的；程序类**原样附报错原文**——不复述、不改写、不截断 |
| 环境 | 跑一次 `tingle doctor` 取装备与版本；它自己都跑不动，就照实记「跑不动」加它的报错原文 |
| 在哪个项目撞上 | 当前工作文件夹对应的那个客户项目 |

**Step 4 · 只问使用者两句，然后整条摆出来等他点头**

只有两句是他独有、AI 取不到的：

1. 你本来想干什么？
2. 你期望看到什么、实际看到的是什么？

会话里他已经说清楚的，**自己填、不要再问一遍**，摆出来时让他核对即可。

然后把**整条记录摆出来**——标题、类型、严重度、经过——请他过目。他说改哪句就改哪句；他说记才记；他说算了就算了、不劝。**没有这一声，不许写。**

**Step 5 · 写台账，报回执**

- 拿下节那两个 token，用 `base +record-batch-create` 写入一条记录（传一行即可）。
- 写成了：把记录链接交给使用者，并告诉他维护者会收到通知——通知由台账侧的自动化发出，本 skill 不发消息、也不需要知道维护者是谁。
- **写不成，不许无声**：见「写不进去怎么办」。

## 报之前先查一遍

写之前，用飞书命令行工具在台账里按关键词搜一次：`base +record-search --keyword "<关键词>" --search-field "标题"`（**`--search-field` 是必填的**，不给它会报参数错；查重就搜「标题」这一栏）。

- **查到同一个问题、这次没有新信息** → 不新建。告诉使用者「这条已经有人报过，现在的状态是 X」，就地结束。
- **查到同一个问题、但这次有新东西**（新的复现路径、更重的后果、另一个场景也中招）→ 仍然不新建，把新信息补进那一条的经过里，注明是补充。
- **查不到** → 新建。

理由：同一个坑被三个人各报一条，维护者看到的是三条待办，而不是「这个坑绊了三个人」——后者才是他需要的信息。

> **判为重复、决定不新建，这一步必停交人。** 把「我认为这跟已有的第 X 条是同一个问题，所以不新建」连同那一条的原文摆给使用者，等他确认。理由：这一步判错了**没有任何人会发现**——被误判成重复的那条反馈就此消失，使用者以为报过了，维护者从未见过它。其余各步判错了，维护者看台账时都还看得出来；只有这一步的错是无声的。

## 写不进去怎么办（失败不许无声）

地址打不开、没有权限、写入报错——任何一种，都**当场把整条记录打印成一段可以直接粘贴的文本**交给使用者，含：标题、类型、严重度、出在哪、具体位置、经过、复现线索（含报错原文）、环境。同时说清**断在哪一步**（地址打不开 / 兜底搜也没有 / 没权限 / 写的时候报了什么错）。

**绝对不许出现的情况**：跟使用者说「已经记下了」，而实际上什么都没有写进去。

## 接口与边界（声明）

- **适用环节**：插件自身问题的回流——任何会话、任何项目、任何时候都可能发生，不属于业务链上的任何一站。
- **input schema**：`会话事实`（本次会话里已发生的事——跑过什么 skill、敲过什么命令、报了什么错、读的哪一段说明；**每次输入不一样**，不登记进任何档案）；`装备快照`（`tingle doctor` 的输出，字符串）；`意图`（使用者本来想干什么，一句话）；`落差`（期望看到什么 vs 实际看到什么，一句话）。
- **output schema**：`记录链接`（写成功时的那条记录的地址，字符串）｜`可粘文本`（写不成时交给使用者的整条全文，字符串，与前者二选一必有其一）；`类型`（枚举：插件毛病 / 质量反馈 / 需求许愿）；`严重度`（枚举：挡住干活 / 有绕法 / 不挡活）；`查重结论`（枚举：新建 / 补进已有第 X 条 / 判为重复不新建）。**可沉淀候选（reusable_candidates）**：无——每一条反馈都是一次具体故障的记录，不是可复用的经验；它的复用发生在维护者改插件那一侧，不在本 skill 的产出里。
- **写回位置**：飞书「tingle-反馈台账」一条记录（地址见「台账在哪」，写死在本页）。本 skill 不在使用者机器上留任何文件。
- **规则层与项目事实**：不挂载品类 / 品牌 / 类型任何规则层（本 skill 不产内容、不碰红线）；所需项目事实字段：无。
- **工具**：飞书命令行工具（搜文件、查记录、写记录）＋ `tingle doctor`。不改任何项目文件、不动项目档案、不碰本地指针。
- **决策档**：**经使用者点头**——记什么、记不记由使用者定；AI 只负责把该填的填满、把话说清楚。
- **复核包**：交人过目时随附——整条记录的全文、判为哪一类与哪一档严重度、以及查重的结果（有没有人报过）。
- **升级条件（命中即停交人）**：①使用者不同意记 → 不记，就地结束；②本页写的地址打不开、兜底按表名又搜出不止一张 → 停，让他选；③台账没有权限、兜底也找不到 → 交可粘文本，**不自行建表**；④判为「与已有某条重复、不新建」→ 停，摆出那一条等他确认；⑤**合规红线不确定**（要报的内容里含客户敏感信息、或不确定能不能写进一张全员可见的表）→ 停，问要不要脱敏后再记；⑥**四层规则冲突** → 停；⑦**缺关键项目事实** → 不停，照实记「取不到」并写明为什么取不到（本 skill 不读项目事实，此项极少出现）；⑧**输出需对外发送** → 本 skill 的每一次写入都是对外发送，故第 4 步的过目本身就是这一条的落实，不另设闸。

## 产出验收判据（DoD）

一次运行合格，当且仅当：

1. 走过 Step 1，判过这是插件的问题而不是项目的问题；
2. 会话里已有的事实**一格都没拿去问人**；
3. 整条记录在写出去之前**摆给使用者看过、并得到明确同意**；
4. 记录单独拎出来读，读得出**是什么坏了、挡不挡活、属于哪一类**；程序类问题**带原始报错原文**；
5. 报之前查过台账，重复的没有新建；
6. 写成功给了链接；写不成给了可粘文本，并说清断在哪一步。

## Quick Reference

| 情形 | 动作 |
|---|---|
| 撞上问题、手上的活还没干完 | 先干完，别岔出去 |
| 撞上问题、活已经卡死 | 当场提议记一条 |
| 判不准是插件的还是项目的 | 当成插件的，摆出来让使用者定 |
| 使用者说「这个 skill 有问题」 | 直接进 Step 1 |
| 使用者说「算了不用记」 | 不记，就地结束，别劝 |
| 台账打不开、兜底搜也没有 | 交可粘文本 + 让他找维护者要权限；**不建表** |
| 同一个问题已经有人报过 | 不新建；有新信息就补进那一条 |
| 写入报错 | 交可粘文本，并说清断在哪一步 |

## Common Mistakes

- **把客户项目的业务问题当插件问题报**——材料缺、客户改口不是插件的毛病；这么报下去，台账会变成杂物间。
- **问使用者「你用的哪个版本」**——版本自己查得到。问了就是把成本推给一个已经被绊了一次的人。
- **复述报错而不附原文**——维护者靠原文定位；复述过的报错等于没有。
- **没等点头就写出去**——记录署他的名、占维护者的注意力，这不是你能替他决定的事。
- **写不进去却说「已经记下了」**——最坏的一种：问题从此消失，且没有任何人知道它消失了。
- **同一个坑反复新建记录**——先查。
- **把整段对话贴进「经过」**——经过是一句话说清什么坏了；细节归复现线索。
- **打不开就新建一张表**——台账只有一张，地址写在本页。

## Red Flags（出现即停，回到五步）

- 「这个毛病挺小的，不值当记」→ 小毛病最容易反复绊人。摆出来，让使用者定。
- 「先把活干完，回头再记」→ 干完就记。「回头」在实践中等于不记。
- 「使用者没说，我猜他想要的是 X」→ 猜的不写。那两句就是拿来问的。
- 「地址打不开，我建一张新的」→ 不建。反馈写进没人看的表里，比不写更糟。
- 「顺手把项目里那个材料问题也一并记了」→ 那不是插件的问题，别混进来。
- 「他刚才说『这什么破东西』，应该算同意记了吧」→ 那是抱怨，不是授权。问一句。
