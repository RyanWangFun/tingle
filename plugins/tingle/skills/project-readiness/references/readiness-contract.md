# tingle 项目就绪契约 · 运行态参考件

> **同事机器运行时以本件为准；版本：锚 schema 2 / 档案 schema 1。**
>
> 本件是 tingle 就绪系统的运行时依据，回答四件事：项目状态怎么存（两层模板）、一个项目对一名成员是否就绪怎么判（三步判定规则）、新 skill 怎么声明自己需要的输入（requirements 声明格式）、多名成员同用一个项目时守什么原则（多人运行原则）。就绪 skill（project-readiness）按本件执行判定与补齐；各 work-skill 的运行级 Step-0 一行调用就绪 skill，不自带判定逻辑；初始化流程照本件模板建项目档案、写本地锚；所有环节共同遵循本件，不各自另定一套。

## 一、两层状态模型与项目档案模板

**模型**：状态分**两层**——

- **项目级 = 飞书「项目档案」**：一项目一份，是该项目的共享真相。记项目身份（id/name）、标签（品类/品牌）、阶段、各 skill 的输入地址、项目级初始化完成日。项目内全部成员共读共用同一份。
- **个人级 = 本地薄锚 `.tingle/state.json`**：每名成员一份，落在该成员自己机器上的项目工作文件夹里。只存三项：锚 schema 版本、项目档案地址、个人级初始化完成日。

一个项目有 N 名成员，就有 **N 份锚 + 1 份档案**。各 skill 的输入地址只记在档案一处——地址变更只改档案，各成员下次运行自动获得新地址，本地锚永不腐烂。锚里不复制任何地址簿：锚只存"项目档案在哪"这一件几乎不变的事实。

两层都只**存事实（地址、日期），不存结论（就绪勾）**——就绪由每名成员每次运行时现算（见「三、就绪判定规则」），永不互相污染；环境状态永远现场查、永不落盘（两层均不含任何 `lark_cli` / `env` / `auth` 之类的环境键）。**模板**（本件给出的，通用、占位、零机密）与**实例**（某具体项目的真值填充版）是两回事——模板随插件公开发布，实例只留在本地（档案实例在该项目的飞书云盘，锚实例在各成员本地工作文件夹）。

**项目档案的载体**：项目云盘**顶层**一份 lark-doc，标题固定为「tingle-项目档案」，正文为约定结构的 JSON 代码块（即下方档案模板的实例化），**一项目一份**。有项目云盘访问权的成员即可发现它；agent 以 lark-doc 读写它；**不建组织级登记库**——不存在集中索引档案的组织层设施，档案随项目云盘走。

**字段命名约定**：**结构性键一律用英文**（`project` / `id` / `name` / `tags` / `initialized_at` / `skills` / `type` / `link` / `base_token` / `table_id` / `folder_token` / `profile_link` 等，凡描述"这是什么种类的容器/属性"的键都用英文，保证解析代码不需要处理双语键名）；**三个业务域键 `品类`、`品牌`、`阶段` 保留中文键名**，因为三者都是团队业务里的既有中文概念，生造英文对应词不会更清楚。skill 的输入名（如 `项目选题上下文`）与 requirements 里的「`就绪判据`」格同理——面向团队的业务中文概念，保留中文键名。此约定是唯一约定，模板与所有实例均遵循，不再有第二种命名风格并存。

**项目档案模板（占位、零客户数据、随插件可公开发布）**：

```json
{
  "tingle_profile_version": 1,
  "project": {
    "id": "<项目短标识，小写英文，工程内部用>",
    "name": "<项目全名，人读>",
    "tags": {
      "品类": {
        "业务线": "<顶层大类：美妆 / 大健康 / 消费品 …>",
        "合规类目": "<决定加载哪套合规红线的那一级：处方药 / OTC / 医疗器械 / 保健食品 / 化妆品 / 一般消费品 …>",
        "产品品类": "<具体产品品类描述，自由文本>"
      },
      "品牌": "<品牌标签，即品牌名字符串>"
    },
    "阶段": "<项目当前阶段，受控初始集：策略期 / 执行中 / 新周期（可扩）>"
  },
  "initialized_at": "<项目级初始化完成日 YYYY-MM-DD；未完成则整个字段不出现>",
  "skills": {
    "<skill_name>": {
      "<input_name>": {
        "type": "lark-doc",
        "link": "<该项目为此输入配好的飞书文档链接>"
      },
      "<input_name_2>": {
        "type": "lark-base",
        "base_token": "<该项目为此输入配好的多维表格 base token>",
        "table_id": "<该项目为此输入配好的表 ID>"
      },
      "<input_name_3>": {
        "type": "lark-drive",
        "folder_token": "<该项目为此输入配好的云盘文件夹 token>"
      }
    }
  }
}
```

**档案字段说明**：

| 字段路径 | 含义 | 是否必填 |
|---|---|---|
| `tingle_profile_version` | 项目档案遵循的档案 schema 版本号（整数），**当前契约规定值为 1**；与当前契约值不一致时按「三、就绪判定规则」判不就绪、路由初始化重建 | 是 |
| `project.id` | 项目短标识（工程内部用） | 是 |
| `project.name` | 项目全名（人读） | 是 |
| `project.tags.品类` | 项目品类（**结构化对象**，含下面三级；非单字符串） | 是 |
| `project.tags.品类.业务线` | 顶层大类（受控枚举：美妆 / 大健康 / 消费品 …），组织归类与跨项目一致性用 | 是 |
| `project.tags.品类.合规类目` | **★决定加载哪套合规红线的那一级★**（受控：处方药 / OTC / 医疗器械 / 保健食品 / 化妆品 / 一般消费品 …）；skill 运行时按此加载品类层红线——这也是为什么不能只存"大健康"（其下处方药/保健品/器械红线完全不同套） | 是 |
| `project.tags.品类.产品品类` | 具体产品品类描述（自由文本） | 是 |
| `project.tags.品牌` | 项目品牌标签（字符串＝品牌名，加载品牌层红线的钥匙） | 是 |
| `project.阶段` | 项目当前阶段（中文键，与品类/品牌同规）。**受控初始集：`策略期` / `执行中` / `新周期`，可扩**。"哪个阶段该跑哪些 skill、是否触发重蒸"的语义映射**尚未定义**（不在任何现有 skill 中，勿去 using-tingle 或本 skill 内寻找），**本件只存字段本身**；阶段值当前的实际用途＝供材料域 skill 做查缺过滤 | 是 |
| `initialized_at` | **项目级**初始化完成日（`YYYY-MM-DD`）——该项目的项目级初始化工序（云盘落点、收料、蒸馏、打标、定阶段、建承接、接线、档案登记）全部完成之日。一个项目只有一个，与各成员锚中的个人级 `initialized_at` 是两回事 | 项目级初始化完成后必填；未完成时此字段不存在 |
| `skills.<skill_name>` | 某个 skill 的输入配置容器，键名为该 skill 的名字（如 `on-trend-radar`） | 该 skill 已配置则必填 |
| `skills.<skill_name>.<input_name>.type` | 该输入的类型，取值仅 `lark-doc` / `lark-base` / `lark-drive` 之一 | 是 |
| `skills.<skill_name>.<input_name>.link` | `type` 为 `lark-doc` 时必填：飞书文档链接 | 视 type 而定 |
| `skills.<skill_name>.<input_name>.base_token` | `type` 为 `lark-base` 时必填：多维表格 base token | 视 type 而定 |
| `skills.<skill_name>.<input_name>.table_id` | `type` 为 `lark-base` 时必填：具体表 ID | 视 type 而定 |
| `skills.<skill_name>.<input_name>.folder_token` | `type` 为 `lark-drive` 时必填：云盘文件夹 token | 视 type 而定 |

**关于 `品类` 为何是结构化对象（而非单字符串）**：品类的系统职责是"加载哪套合规红线的钥匙"，而团队业务横跨美妆/大健康/消费品，规则差异最大处在大健康内部（处方药 vs 保健食品 vs 医疗器械，红线完全两套）——所以品类必须结构化到"规则开始不同的那一级"，即 `合规类目`。三级中 `合规类目` 承重（决定加载哪套品类层红线），`业务线` 管组织归类，`产品品类` 只作描述。**范围界定**：本件只定 `品类` 的**结构**（三级 + `业务线/合规类目` 为受控值）；"有哪些合法的业务线/合规类目取值、各自映射到哪套红线"这套**受控词表 + 规则映射**属于规则系统（品类层规则库）的设计，不在本状态契约内——本件只记某项目的品类填了什么，不定义品类全集。

## 二、本地锚模板

**锚的落位与命名**：固定命名为 `.tingle/state.json`，以**每名成员自己机器上的项目工作文件夹**为根——即每名成员在自己的项目工作文件夹下建 `.tingle/` 子目录，锚就是其中的 `state.json`。**锚每人一份**：不存在全局共享的锚，也不存在按项目 ID 索引的集中锚库；就绪 skill（由运行级 Step-0 一行调用）从当前项目工作文件夹的 `.tingle/state.json` 读锚。

**本地锚模板（占位、零客户数据、随插件可公开发布）**：

```json
{
  "tingle_state_version": 2,
  "profile_link": "<本项目「tingle-项目档案」lark-doc 的飞书文档链接>",
  "initialized_at": "<该成员个人级初始化完成日 YYYY-MM-DD>"
}
```

锚**仅此三项**，没有第四个字段——不存项目身份、不存标签、不存任何输入地址（那些都在档案里）。

**锚字段说明**：

| 字段 | 含义 | 是否必填 |
|---|---|---|
| `tingle_state_version` | 本地锚遵循的锚 schema 版本号（整数），**当前契约规定值为 2**；与当前契约值不一致时按「三、就绪判定规则」判不就绪、路由初始化重建 | 是 |
| `profile_link` | **项目档案地址**——本项目云盘顶层「tingle-项目档案」文档的飞书链接。锚只存这一件几乎不变的事实；一切输入地址在档案里，不在锚里 | 是 |
| `initialized_at` | **个人级**初始化完成日（`YYYY-MM-DD`）——该成员本人在自己机器上完成个人级初始化工序（锚项目/建工作文件夹、装备预装、权限、写本锚）之日。每名成员各有一个，与档案中的项目级 `initialized_at` 互不混同 | 是 |

**版本字段与不匹配处理**：当前契约规定——锚 `tingle_state_version` 取值 **2**，档案 `tingle_profile_version` 取值 **1**。任一版本字段与当前契约规定值不一致 → 该成员对该项目**判不就绪** → **路由初始化按当前模板重建**（锚版本不匹配重建锚，档案版本不匹配重建/升级档案）。未来版本升级的迁移机制归更新机制设计，不在本件范围。

## 三、就绪判定规则（三步）

**执行者**：三步判定引擎在**就绪 skill**（project-readiness）内**唯一实现**——全家族只此一份。**运行级 Step-0**——每个 work-skill 自带的运行前检查——只是触发：**该 skill 每次运行前**一行调用就绪 skill 执行本节三步。入口级的 **using-tingle 不是三步的执行者**：它只在会话开启时锚定项目维度（在哪个项目里工作）、扫描本地锚、对未初始化项目路由初始化流，不做单次运行的三步判定。

**判定结论**：三步全过 = 本次运行就绪，可直接运行；任一步不过 = 不就绪，转入初始化/修复，**不运行这一次**。三步顺序不可颠倒——环境是最基础依赖，环境不全，后面档案/资源也读不了。

**就绪按人各自判**：同一个项目对甲成员就绪、对乙成员可能不就绪（装备、授权、锚都是个人的）。每名成员的 Step-0 在其自己的机器与自己的飞书账号下各自触发就绪 skill 判定，互不代表、互不复用结论。

**第一步·环境（现场查，永不落盘）**

以下各项同时成立，环境判定就绪：

1. 按**官方装备清单**逐项核查已装齐（清单 v1＝lark-cli 二进制、lark-* skill 目录全套、lark-cli 授权有效，加 tingle 插件自身已装；清单按**按需倒推**原则可扩展——新 skill 入驻带新依赖时，随其 requirements 声明进清单）。其中 **lark 全套为必查最小集**，当前的机械核查法：`command -v lark-cli` 有输出（lark-cli 二进制已安装）；`~/.claude/skills/lark-*` 或 `~/.agents/skills/lark-*` 路径下存在完整一套 lark 相关 skill 目录；
2. `lark-cli auth status` 返回已授权状态。

任一项不成立，环境判定未就绪；不必再看第二、三步，先补装/授权。

**第二步·锚与档案**

按顺序核查，以下各项同时成立才通过：

1. **锚在**：当前项目工作文件夹下 `.tingle/state.json` 存在，且 `tingle_state_version`、`profile_link`、`initialized_at` 三字段齐全非空；
2. **锚版本匹配**：`tingle_state_version` 值等于 **2**（当前契约锚版本）；
3. **档案打得开**：以 lark-doc 打开 `profile_link` 指向的文档，能读取正文中的 JSON 代码块并成功解析；
4. **档案版本匹配**：档案 `tingle_profile_version` 值等于 **1**（当前契约档案版本）；
5. **档案项目字段齐**：`project.id`、`project.name` 存在且非空；`project.tags.品类` 下三级（`业务线`/`合规类目`/`产品品类`）均存在且非空；`project.tags.品牌` 存在且非空；`project.阶段` 存在且非空；项目级 `initialized_at` 字段存在；
6. **目标 skill 输入齐**：本次要运行的 skill（按其名字）在档案 `skills` 段下有对应键，且该键下每一个输入字段齐全——`type` 有值，且按 `type` 对应的值字段有值（`lark-doc` → `link`；`lark-base` → `base_token`+`table_id`；`lark-drive` → `folder_token`）。

任一项不成立，判定不就绪：第 2、4 条（版本不匹配）→ **路由初始化重建**（见「二、本地锚模板」末「版本字段与不匹配处理」）；其余各条 → 路由初始化补齐。

**第三步·验（地址可达 + 就绪判据）**

对目标 skill 在档案 `skills` 段下记录的**每一个输入**，逐个执行以下两项：

1. **地址当场打得开**：按 `type` 对该地址轻量访问一次——`lark-doc` 读取文档标题、`lark-base` 读取表的基本信息、`lark-drive` 列出文件夹——访问成功即通过。链接失效、资源被删、**当前成员权限不足**都在此项暴露：成员飞书账号对项目资源的访问权这一前置检查项，即在此步自然覆盖；
2. **就绪判据逐条过**：该输入在其 skill 的 requirements 里声明的每一条「就绪判据」（见「四、requirements 声明格式」），当场验证成立。未声明就绪判据的输入，只做第 1 项。

任一输入任一项不过，判定不就绪，转入修复：地址失效 → 更新档案中对应配置；判据不过且该输入标有 `produced_by` → 修复路由指向该生产者 skill 重产此输入（见「四、requirements 声明格式」）；无 `produced_by` 的输入 → 路由初始化/人工修复。

## 四、requirements 声明格式

任何新 skill 接入 tingle 就绪系统 = 在自己 SKILL.md 里按本节格式声明一段 + 项目初始化/补齐时在该项目**项目档案**的 `skills` 段按声明多登记一块，本件主体不改。

每个 skill 在自己的 SKILL.md 里声明的 `requirements`，是项目档案里 `skills.<skill_name>` 那一层结构的**"只留类型与判据、不留值"版**——用来说明"这个 skill 需要哪些输入、各是什么类型、内容达到什么状态才算可用、由谁生产"；值（具体链接/token）由项目档案负责填。

**格式**：

```json
{
  "requirements": {
    "<input_name>": {
      "type": "lark-doc",
      "就绪判据": ["<内容级可判中文句>", "<可多条，逐条可判>"],
      "produced_by": "<生产该输入的 skill 名>"
    },
    "<input_name_2>": { "type": "lark-base" },
    "<input_name_3>": { "type": "lark-drive" }
  }
}
```

`type` 为必填，取值集为 `lark-doc` / `lark-base` / `lark-drive` 三值。「`就绪判据`」与 `produced_by` 为**两个可选格**，规则如下：

- **`就绪判据`（可选）**：值为一条或多条**内容级可判中文句**的列表——每句描述"这项输入的内容处于可用状态"的一个检验条件，且可当场判成立/不成立（如"某八个字段段落齐""存在运行当天采集的记录"）。就绪 skill（由运行级 Step-0 一行调用）在「三、就绪判定规则」第三步**逐条验证**这些判据；未声明判据的输入，第三步仅验地址可达。判据只写**内容级**条件（字段齐不齐、记录新不新、结构对不对），不写环境或权限条件——那分别是第一步与第三步第 1 项的既有职责，不在判据里重复。
- **`produced_by`（可选）**：值为**生产该输入的 skill 名**（如蒸馏产物之于 `context-distill`）。作用是**修复路由**——当该输入缺失或判据不过时，就绪 skill 据此给出"调 `<produced_by>` 重产此输入"的修复指向。**无 skill 生产者的输入不标**（如人工配置的承接表、外部数据底座供给的表）；不标者缺失时路由初始化或人工修复。

**与项目档案的对应关系**（同一套字段，一边记类型与判据、一边记值）：

| 位置 | 记什么 | 出现的字段 |
|---|---|---|
| SKILL.md 的 `requirements.<input_name>` | 这个 skill **需要**的输入：类型 + 内容级判据 + 生产者 | `type`（取值 `lark-doc` / `lark-base` / `lark-drive`）、`就绪判据`（可选）、`produced_by`（可选） |
| 项目档案的 `skills.<skill_name>.<input_name>` | 这个项目**已配好**的输入值 | `type` 相同 + 按 type 对应的值字段：`lark-doc` → `link`；`lark-base` → `base_token`+`table_id`；`lark-drive` → `folder_token` |

两者共享同一个 `<input_name>` 命名空间与同一个 `type` 取值集合——requirements 只声明"要什么类型、内容达标线在哪、谁产的"，不出现 `link`/`base_token`/`table_id`/`folder_token` 这些值字段（那是项目档案的职责）；项目档案只记值，不出现 `就绪判据`/`produced_by`（那是 requirements 的职责）。**就绪 skill**（由运行级 Step-0 一行调用）判定"该 skill 输入是否齐全"时，正是拿 requirements 里声明的 `<input_name>` 逐一去项目档案的 `skills.<skill_name>` 下核对是否存在且按其 `type` 对应的值字段齐全（即「三、就绪判定规则」第二步第 6 条），再对每个输入验地址可达并逐条过其声明的就绪判据（即「三、就绪判定规则」第三步）。

## 五、多人运行原则

一个项目多名成员共用时，按以下原则运行：

- **N 锚 1 档案**：一个项目 N 名成员 = **N 份锚 + 1 份档案**。档案是项目共享真相，全员共读共用同一份；锚是个人的，各自落在自己机器上。各 skill 的输入地址只记在档案一处——地址变更只改档案，各成员下次运行自动获得新地址。成员加入已初始化的项目时，只做个人级工序（装备预装、权限、写本地锚指向档案），项目级全部跳过——读到档案即知该项目已初始化。
- **就绪按人各自判**：同一个项目对甲成员就绪、对乙成员可能不就绪（装备、授权、锚都是个人的）。每名成员在自己的机器与自己的飞书账号下各自触发就绪判定，互不代表、互不复用结论。
- **锚每人一份**：不存在全局共享的锚，也不存在按项目 ID 索引的集中锚库；每名成员的锚就是自己项目工作文件夹下的 `.tingle/state.json`。
- **承接表并发原则**：多名成员可能同时向同一张承接表（work-skill 输出落点的共享表）写入。规则：承接表**只追加（append-only）**，不修改、不删除已有行；**写入前按去重键查重**，表中已有同键行则跳过、不重复写入；具体去重键由各 skill 自己的 io-contract 定义。
