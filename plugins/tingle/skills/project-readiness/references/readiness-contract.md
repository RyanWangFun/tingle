## 一、两层状态模型与项目档案模板

**模型**：状态分**两层**——

- **项目级 = 飞书「项目档案」**：一项目一份，是该项目的共享真相。记项目身份（id/name）、标签（品类/品牌）、阶段、**项目云盘地址**、各 skill 的输入与输出地址、项目级初始化完成日。项目内全部成员共读共用同一份。
- **个人级 = 本地指针 `.tingle/state.json`**：每名成员一份，落在该成员自己机器上的项目工作文件夹里。只存三项：本地指针 schema 版本、项目档案地址、个人级初始化完成日。

一个项目有 N 名成员，就有 **N 份本地指针 + 1 份档案**。项目云盘地址与各 skill 的输入、输出地址都只记在档案一处——地址变更只改档案，各成员下次运行自动获得新地址，**没有任何成员会拿着一个过期的地址去干活**。本地指针里不复制任何地址簿：本地指针只存"项目档案在哪"这一件几乎不变的事实。**本地除本地指针之外还有一份只读缓存**（见「二、本地指针模板」末「本地缓存」）——它是云盘那两件的副本，**每次会话重拉：拉到就整体覆盖，拉不到就当场清空、只留一行失效说明，绝不留旧副本**。它**不是第三层状态**，也不改变"地址只在档案一处"这件事。

两层都只**存事实（地址、日期），不存结论（就绪勾）**——就绪由每名成员每次运行时现算（见「三、就绪判定规则」），永不互相污染；环境状态永远现场查、永不落盘（两层均不含任何 `lark_cli` / `env` / `auth` 之类的环境键）。**模板**（本件给出的，通用、占位、零机密）与**实例**（某具体项目的真值填充版）是两回事——模板随插件公开发布，实例只留在本地（档案实例在该项目的飞书云盘，本地指针实例在各成员本地工作文件夹）。

**项目档案的载体**：项目云盘**顶层**一份 lark-doc，标题固定为「tingle-项目档案」，正文为约定结构的 JSON 代码块（即下方档案模板的实例化），**一项目一份**。有项目云盘访问权的成员即可发现它；agent 以 lark-doc 读写它；**不建组织级登记库**——不存在集中索引档案的组织层设施，档案随项目云盘走。

**字段命名约定**：**结构性键一律用英文**（`project` / `id` / `name` / `tags` / `initialized_at` / `folder_token` / `skills` / `inputs` / `outputs` / `type` / `link` / `base_token` / `table_id` / `profile_link` 等，凡描述"这是什么种类的容器/属性"的键都用英文，保证解析代码不需要处理双语键名）；**三个业务域键 `品类`、`品牌`、`阶段` 保留中文键名**，因为三者都是团队业务里的既有中文概念，生造英文对应词不会更清楚。skill 的输入名 / 落点名（如 `<某中文输入名>`）与 requirements 里的「`就绪判据`」格同理——面向团队的业务中文概念，保留中文键名。此约定是唯一约定，模板与所有实例均遵循，不再有第二种命名风格并存。**模板里的 `<input_name>` 与 `<落点名>` 只是占位写法的不同，不代表两类叶子键的命名规则不同**——两者同属叶子层业务名，实例里一律填中文业务名。

**项目档案模板（占位、零客户数据、随插件可公开发布）**：

```json
{
  "tingle_profile_version": 2,
  "project": {
    "id": "<项目短标识，小写英文，工程内部用>",
    "name": "<项目全名，人读>",
    "tags": {
      "品类": {
        "业务线": "<顶层大类：美妆 / 大健康 / 消费品 …>",

        },
        "<input_name_3>": {
          "type": "lark-drive",

        }
      }
    }

```

**档案字段说明**：

| 字段路径 | 含义 | 是否必填 |
|---|---|---|
| `tingle_profile_version` | 项目档案遵循的档案 schema 版本号（整数），**当前契约规定值为 2**；与当前契约值不一致时按「三、就绪判定规则」判不就绪、路由初始化**迁移**（就地覆盖这一份，不新建——见下方「档案 1 → 2 的迁移动作」） | 是 |
| `project.id` | 项目短标识（工程内部用） | 是 |
| `project.name` | 项目全名（人读） | 是 |
| `project.tags.品类` | 项目品类（**结构化对象**，含下面三级；非单字符串） | 是 |
| `project.tags.品类.业务线` | 顶层大类（受控枚举：美妆 / 大健康 / 消费品 …），组织归类与跨项目一致性用 | 是 |
| `project.tags.品类.合规类目` | **★决定加载哪套合规红线的那一级★**（受控：处方药 / OTC / 医疗器械 / 保健食品 / 化妆品 / 一般消费品 …）；skill 运行时按此加载品类层红线——这也是为什么不能只存"大健康"（其下处方药/保健品/器械红线完全不同套） | 是 |
| `project.tags.品类.产品品类` | 具体产品品类描述（自由文本） | 是 |
| `project.tags.品牌` | 项目品牌标签（字符串＝品牌名，加载品牌层红线的钥匙） | 是 |
| `project.阶段` | 项目当前阶段（中文键，与品类/品牌同规）。**受控初始集：`策略期` / `执行中` / `新周期`，可扩**。"哪个阶段该跑哪些 skill、是否触发重蒸"的语义映射**尚未定义**（不在任何现有 skill 中，勿去 using-tingle 或本 skill 内寻找），**本件只存字段本身**；阶段值当前的实际用途＝供材料域 skill 做查缺过滤 | 是 |
| `folder_token`（**顶层**） | **本项目飞书云盘顶层文件夹的 token**——项目一切产物的落点根。**这是"项目云盘在哪"的唯一真相源**：全系统凡需要项目云盘地址（重蒸 / 修复路由传参、落点定位、按标题搜档案）一律从此处取，不得从 `skills` 段下某个 `lark-drive` 输入 / 落点的 `folder_token` 反推——那些记的是某个输入或落点自己的文件夹，不是项目云盘根，同一事实两处可读即两个维护点 | 是 |
| `initialized_at` | **项目级**初始化完成日（`YYYY-MM-DD`）——该项目的项目级初始化工序（云盘落点、打标、定阶段、收料、转可读、蒸馏、档案登记）全部完成之日。一个项目只有一个，与各成员本地指针中的个人级 `initialized_at` 是两回事 | 项目级初始化完成后必填；未完成时此字段不存在 |
| `skills.<skill_name>` | 某个 skill 的地址配置容器，键名为该 skill 的名字（如 `<某 work-skill 名>`）。其下**恰两个子容器** `inputs` / `outputs`，不得再把输入项直接挂在本层 | 该 skill 已配置则必填 |
| `skills.<skill_name>.inputs` | 该 skill **要读的东西**的地址容器：键为输入名，值为一份地址配置 | 该 skill 有输入则必填 |
| `skills.<skill_name>.inputs.<input_name>.type` | 该输入的类型，取值仅 `lark-doc` / `lark-base` / `lark-drive` 之一 | 是 |
| `skills.<skill_name>.inputs.<input_name>.link` | `type` 为 `lark-doc` 时必填：飞书文档链接 | 视 type 而定 |
| `skills.<skill_name>.inputs.<input_name>.base_token` | `type` 为 `lark-base` 时必填：多维表格 base token | 视 type 而定 |
| `skills.<skill_name>.inputs.<input_name>.table_id` | `type` 为 `lark-base` 时必填：具体表 ID | 视 type 而定 |
| `skills.<skill_name>.inputs.<input_name>.folder_token` | `type` 为 `lark-drive` 时必填：云盘文件夹 token（**该输入自己的文件夹，不是项目云盘根**——项目云盘根见顶层 `folder_token`） | 视 type 而定 |
| `skills.<skill_name>.outputs` | 该 skill **要写的地方**的地址容器：键为落点名，值为一份地址配置。**本项目为该 skill 批准的产出落点在此登记**——落点地址与输入地址同规，只记在档案这一处，skill 不自行选址 | 该 skill 有产出落点则必填 |
| `skills.<skill_name>.outputs.<落点名>.type` | 该落点的类型，取值仅 `lark-doc` / `lark-base` / `lark-drive` 之一（与输入同一取值集） | 是 |
| `skills.<skill_name>.outputs.<落点名>.link` | `type` 为 `lark-doc` 时必填：飞书文档链接 | 视 type 而定 |
| `skills.<skill_name>.outputs.<落点名>.base_token` | `type` 为 `lark-base` 时必填：多维表格 base token | 视 type 而定 |
| `skills.<skill_name>.outputs.<落点名>.table_id` | `type` 为 `lark-base` 时必填：具体表 ID | 视 type 而定 |
| `skills.<skill_name>.outputs.<落点名>.folder_token` | `type` 为 `lark-drive` 时必填：云盘文件夹 token（**该落点自己的文件夹，不是项目云盘根**） | 视 type 而定 |

**关于 `品类` 为何是结构化对象（而非单字符串）**：品类的系统职责是"加载哪套合规红线的钥匙"，而团队业务横跨美妆/大健康/消费品，规则差异最大处在大健康内部（处方药 vs 保健食品 vs 医疗器械，红线完全两套）——所以品类必须结构化到"规则开始不同的那一级"，即 `合规类目`。三级中 `合规类目` 承重（决定加载哪套品类层红线），`业务线` 管组织归类，`产品品类` 只作描述。**范围界定**：本件只定 `品类` 的**结构**（三级 + `业务线/合规类目` 为受控值）；"有哪些合法的业务线/合规类目取值、各自映射到哪套红线"这套**受控词表 + 规则映射**属于规则系统（品类层规则库）的设计，不在本状态契约内——本件只记某项目的品类填了什么，不定义品类全集。

## 二、本地指针模板

**本地指针的落位与命名**：固定命名为 `.tingle/state.json`，以**每名成员自己机器上的项目工作文件夹**为根——即每名成员在自己的项目工作文件夹下建 `.tingle/` 子目录，本地指针就是其中的 `state.json`。**本地指针每人一份**：不存在全局共享的本地指针，也不存在按项目 ID 索引的集中本地指针库；就绪 skill（由运行级 Step-0 一行调用）从当前项目工作文件夹的 `.tingle/state.json` 读本地指针。

**本地指针模板（占位、零客户数据、随插件可公开发布）**：

```json
{
  "tingle_state_version": 2,
  "profile_link": "<本项目「tingle-项目档案」lark-doc 的飞书文档链接>",
  "initialized_at": "<该成员个人级初始化完成日 YYYY-MM-DD>"
}
```

本地指针**仅此三项**，没有第四个字段——不存项目身份、不存标签、不存项目云盘地址、不存任何输入 / 输出地址（那些都在档案里），**也不存本地缓存的任何状态**（缓存新不新鲜写在缓存文件自己的内容里，见本节末「本地缓存」）。

**本地指针字段说明**：

| 字段 | 含义 | 是否必填 |
|---|---|---|
| `tingle_state_version` | 本地指针的结构版本号（整数），**当前契约规定值为 2**；与当前契约值不一致时按「三、就绪判定规则」判不就绪、路由初始化重建 | 是 |
| `profile_link` | **项目档案地址**——本项目云盘顶层「tingle-项目档案」文档的飞书链接。本地指针只存这一件几乎不变的事实；项目云盘地址与一切输入 / 输出地址都在档案里，不在本地指针里 | 是 |
| `initialized_at` | **个人级**初始化完成日（`YYYY-MM-DD`）——该成员本人在自己机器上完成个人级初始化工序（本地指针项目/建工作文件夹、装备预装、权限、写本本地指针）之日。每名成员各有一个，与档案中的项目级 `initialized_at` 互不混同 | 是 |

**版本字段与不匹配处理**：当前契约规定——本地指针 `tingle_state_version` 取值 **2**，档案 `tingle_profile_version` 取值 **2**。任一版本字段与当前契约规定值不一致 → 该成员对该项目**判不就绪** → 路由初始化处理，但两者做法不同：

- **本地指针版本不匹配** → 按本件本地指针模板**重建本地指针**（本地动作）。本地指针是个人的、只存三项几乎不变的事实，且没有任何别处记着它的地址，重建无损失。
- **档案版本不匹配** → **走迁移，不新建**。档案是全项目共享的那一份，它的链接已被每名成员的本地指针记着；新建一份就是换了链接，全员的本地指针仍指向旧的那份（理由详见下方「为什么是原处覆盖」）。档案 **1 → 2** 的迁移动作见本节下方；**更通用的 N → N+1 迁移机制仍待定**，到时另立，不得拿下面这套 1 → 2 的具体动作去套别的版本跨度。

### 档案 1 → 2 的迁移动作（五步，按序执行，不增删步）

**适用范围**：**只覆盖版本 1 → 2**。读到的档案版本值**不是 1**（也不是 2）时：**停**，报出读到的版本值与档案链接，交使用者判断——不套用下面这套动作、不自行推断该怎么改，也不因为"总归要升到 2"就照着改。

**前提**：这是一个**已经初始化过、正在用**的项目——档案里的项目身份、标签、阶段、各输入地址都是真值，云盘里的材料与产物都在。迁移只换档案这一份文件的结构，**不重跑任何前置工序**（**道10 本身要建的那两件仍都要有着落**——道10 建的是项目档案 ＋ 项目总索引，迁移既然只跑道10，两件都在本节范围内，见第 4 步；那不是前置工序）。

**第 0 步 · 先取项目云盘坐标**（第 2 步存档、第 3 步写顶层字段都要用它）。版本 1 的档案**顶层没有 `folder_token`**，这个值记在 `skills.context-distill.项目云盘.folder_token`——**从旧档案的这个路径把它读出来**。这是**读旧档案的内容**（档案本就是这个项目的状态记录，本件通篇都在读它），**不是读某个技能 SKILL.md 里的 `requirements` 声明**；「初始化不读技能的声明」禁的是后者，本步不违反。**它也不与顶层 `folder_token` 字段说明里「不得从 `skills` 段反推项目云盘根」那条冲突**：那条管的是**版本 2 的档案**——它有顶层字段，`skills` 段下的 `folder_token` 都是某个输入 / 落点自己的文件夹，反推就是取错值；而版本 1 的档案没有顶层字段，`项目云盘` 这个输入名所指的本来就是项目云盘根本身，是当时唯一记着这个值的地方。**这是仅限"读版本 1 旧档案"的一次性例外**——顶层 `folder_token` 一旦写成，此后一律只从顶层取。**该路径在旧档案里也不存在时：停，向使用者问明本项目云盘顶层文件夹是哪一个（要到 `folder_token` 或可定位的链接），得到答复再往下走——不猜文件夹、不拿别的文件夹顶替，也不因为取不到值就把顶层 `folder_token` 略过不写。**

**第 1 步 · 读旧档案**：以 lark-doc 打开这份档案——**初始化入径下**＝本地指针里 `profile_link` 指向的那份；**新成员加入路径下**＝使用者刚粘贴（或按标题在云盘顶层搜到）的那条链接，此时这名成员**还没有本地指针**。读出正文 JSON 全文并逐字留底——后面三步都以这份底为准。

**第 2 步 · 复制一份存档**：把旧 JSON **原样**另存为**另一份文档**，放进项目云盘的 `_tingle/` 子文件夹（没有则建），标题带上旧版本号与迁移日期，形如 `项目档案-v1-20260803`。存档件有两条硬约束：

- **必须移出云盘顶层，且必须改标题**——档案是靠"云盘顶层 + 固定标题「tingle-项目档案」"寻址的（见「一、两层状态模型与项目档案模板」的「项目档案的载体」段）；顶层若出现第二份同标题文档，按标题搜就是多命中、即停，此后新成员再也加不进这个项目。
- **不许把旧 JSON 附在新档案正文底部当"历史版本"**——档案的判定动作是「读取正文中的 JSON 代码块并解析」；一份正文里有两个 JSON 代码块，解析会取到其中一个而**不报错**，从此这个项目的状态可能是错的而没有任何人知道。存档只能是另一份文档，没有第二种存法。

**第 3 步 · 原档案就地覆盖成新结构**：**链接、位置、标题全不变**，只把正文的 JSON 换成版本 2 的形状——

- `tingle_profile_version`：1 → **2**；
- **顶层新增 `folder_token`**：值＝第 0 步取到的那个；
- `skills.<skill_name>` 下原本直挂的各输入项，**整体缩进一层包进 `inputs`**（键名与值一字不改，只改层级）；
- `outputs` 段：旧档案没有落点登记，**迁移不发明落点**——只有使用者在本次放行的待建内容清单里明确给出了落点，才照实登记；否则本次**不写 `outputs`**；等某个 skill 真要写入时再按 `skills.<skill_name>.outputs` 的规矩补登记。**"本次不写"≠"日后不必登记"，更不等于"落点可以一直空着"**——这里豁免的只有**迁移这一次**：迁移没有目标 skill、根本不走第二步第 6 条，所以不因 `outputs` 为空判不合格。**日后那个声明了落点的 skill 真要运行时，落点没登记就是不就绪**：第 6 条当场拦住它、本次不跑，走道10 补登记，地址仍由使用者在放行清单里给出，**也不许自行选址**。
- `project`（`id` / `name` / `tags` / `阶段`）与 `initialized_at`：**原值照搬**，不重新问人、不重新认定。

**第 4 步 · 项目总索引按现状建出或核齐**：迁移一旦完成，这就是一个**版本 2 的项目**；而版本 2 的状态模型要求项目云盘顶层有一份「tingle-项目索引」——道10 建的本就是两件（项目档案 ＋ 项目总索引），迁移只跑道10，这一件同样要有着落，不能只换档案就收工。

- **顶层没有这一份 → 按道10 的规矩建出来**：标题固定「tingle-项目索引」、落项目云盘顶层，五段行式，建出时三行（认知件 / 原料 / 内务件）；某一类这次没东西可指，**那一行照留**、入口链接写「—」，「一句这是什么」后注明本项目此类的状态。
- **顶层已有一份 → 不重复建**（顶层出现第二份同标题文档即多命中，与存档件那条硬约束同一个坑）：改为**按现状核那三行齐不齐**——缺哪行补哪行、已有行不动，并把补出来的那一行的「最近更新」填成当天。

**为什么迁移也非建不可**：不建，就会留下一个**没有总索引的版本 2 项目**。`raw/_可读件/`、`raw/_台账/` 这些内务件正是由总索引「内务件」那一行覆盖的（见 `context-distill` 参考件「无孤儿文件不变量」）——没有总索引，它们**无人覆盖，直接违反无孤儿文件不变量**；下游想知道"这个项目有哪几类东西、每一类从哪儿进去"，也无处可查。

**为什么这不算"重跑道4–9"**（免得下一个人拿"迁移要跳过道4–9"来驳这一步）：建总索引**不重新收料、也不重新蒸馏**，只是把一份缺失的索引**按现状**建出来——三行的入口分别指向**已经存在的**认知件索引与 `raw/索引.md`，记的是这个项目现有的东西，不产生任何新产物。跳过道4–9 的理由是"重跑是白干、还可能覆盖掉正在用的产物"，这条理由**对建一份缺失的索引不成立**：它既不是白干（此前根本没有这份索引），也覆盖不掉什么（顶层已有一份时明令不重复建、只补缺行）。

**第 5 步 · 前置工序一律不重跑**：云盘落点、打标、定阶段、收料、转可读、蒸馏——这些在这个项目上早已完成，迁移只改档案这一份文件（**上一步的总索引不在此列**：那不是重跑某一道，是把缺的那份索引按现状建出来）。覆盖完按「三、就绪判定规则」复验（第二步第 1–5 条，其中第 5 条现在含顶层 `folder_token`），全过、**且按 `project-readiness` 的「产出验收判据（DoD）」逐条过一遍之后**（本入径跑了道10，第 10 条同样适用），才算恢复就绪——**"各查全过"本身不是充分条件**。**本地指针的处置分两种**：**初始化入径下本地指针不必动**——链接没变，`profile_link` 仍然有效；只有本地指针自身版本也不匹配时才另按上面「本地指针版本不匹配」重建本地指针。**新成员加入路径下这名成员本就没有本地指针**，迁移完成后**必须**按加入路径写本地指针指向这份档案，不得因为上面那句"本地指针不必动"就跳过。

**为什么是"原处覆盖"，而不是"新建一份落到顶层"**：每名成员的本地指针里存的是**档案链接**（`profile_link`），本地指针不会自己更新。新建一份就是新链接——全员的本地指针仍指向被移走的旧档案，谁打开都还是旧版本、还是判不就绪、还是被路由来做一次迁移，一圈圈转，而每转一圈就多一份存档。就地覆盖则一次到位：链接没变，全员下次运行读到的就是新结构，谁都不必动自己的本地指针。

### 本地缓存（只读副本；与本地指针同住 `.tingle/`，但两回事）

**它是什么**：本地除本地指针之外的一份**只读缓存**——本次会话从云盘拉到的**项目档案**与**项目总索引**的副本，供开工时快速回答"这个项目里有什么"，免得每次都联网去云盘拉一遍。**它不是状态模型的第三层**：状态仍只有两层（项目级档案 / 个人级本地指针）。缓存不是任何事实的家，只是"这次拉到的一份副本"。

**存哪两件、落哪两个路径**（路径写死，不得另择、不得增减）：

| 缓存件 | 路径（相对项目工作文件夹） | 内容 |
|---|---|---|
| 项目档案副本 | `.tingle/cache/项目档案.json` | 云盘顶层「tingle-项目档案」正文 JSON 的原样副本 |
| 项目总索引副本 | `.tingle/cache/项目索引.md` | 云盘顶层「tingle-项目索引」正文的原样副本 |

**什么时候刷**：**每次会话启动、以及会话中途每次重走入口三步之后**，各重拉一次——由会话入口（`using-tingle`）在走完三步之后顺手尝试，**不由本 skill、也不由任何 work-skill 负责**。（入口那一侧本就规定"工作文件夹一切换就重走三步"，所以中途换项目文件夹后同样刷一次；不刷的话，新项目的缓存里装的会是上一个项目的东西。）

**两件怎么寻址**：先按本地指针里 `profile_link` 打开「tingle-项目档案」；再据**档案顶层 `folder_token`** 定位项目云盘顶层，按固定标题「tingle-项目索引」拉总索引。**拉到 → 整体覆盖写入**上面那两个文件。缓存的寿命不超过一个会话——没有"长期存着的那一份"。

**取地址算不算"判读"——界线写在这里，免得下一个人在同一处纠结**：入口的"只搬运、不判读"指的是**不据档案内容做任何判定**——不判就绪、不取标签与阶段、不下任何结论。**从刚拉到的档案里取一个地址字段（`folder_token`）以定位第二件，属搬运动作本身，不构成判定**，与"不判读"不冲突。

**本地指针不在时整段跳过**：入口 Step 2 判出本地指针缺失或不可解析时没有 `profile_link`，这一步**不执行，也不创建缓存目录与那两个文件**——那是个尚未初始化的项目，不该被入口凭空留下两个只含失效说明的文件。**曾初始化过、本地指针后来缺失或损坏的，同样整段跳过**：此时那两个文件里可能还留着上次的旧内容，本步既不覆盖也不清空它——这一情形由下面「什么时候允许读它」的兜底接住（问不出"本次入口跑过并拉到了吗"，即当作没有缓存），不在这里额外加动作。

**拉不到怎么办**：**那两个文件若已存在，把内容清空、各只留一行说明**（不存在则不必创建——没有旧副本要销毁，就没有要做的事），**不阻断开工。** 说明行的文案固定为：

> `本缓存已失效：本次会话未能从云盘拉取。请直接读云盘，不要使用任何旧副本。`

清完照常往下走，不重试、不报错。入口原本只碰本地文件、永不失败，刷缓存是加上去的一层加速，不得把它变成入口的新失败点。

**为什么是清空、而不是打一个"陈旧"标记**：标记这种做法，要求后面每一个想读缓存的动作**先记得去看一眼标记、并且愿意遵守它**——那是一条需要被遵守的提醒，不是一条走不通的路。清空之后，旧数据在物理上已经不在了：**"拿旧的顶上"不是被禁止，是做不到**。同时两个文件仍然在原位，打开就知道它为什么是空的，不会被当成故障或"文件丢了"。

**没有第三个缓存文件**：不设标记件、不记拉取时刻——缓存新不新鲜，看缓存文件自己的**内容**、再加上"本次会话入口那一步跑过并拉到了吗"这个**在场事实**即可判（判法见下方「什么时候允许读它」）。本地指针里同样不记任何缓存状态——本地指针仍恰三项。

**什么时候允许读它**：下面两条**同时**成立时，"想看一眼这个项目里有什么"这类**浏览**动作才可以直接读缓存，不必再联网——

1. 文件里有**正文内容**（**只剩那行失效说明的不算**——清空后的文件不是空文件，别把它读成"有内容"）；
2. 这份内容确实是**本次会话**拉到的。

**第 2 条不能想当然。**「有内容就等于本次刚拉到」只在"入口每次会话都跑过刷缓存"时才成立，而这个前提**并不总是真**：Codex 侧的 SessionStart hook 未获使用者信任时入口不会自动跑；另有会话中途换过项目文件夹、未经入口直接调某个 skill、清空动作自身没做成、以及**曾初始化过、本地指针后来缺失或不可解析**（刷缓存整段跳过，旧内容原封留在原处，既没被覆盖也没被清空）几种情形。**凡不确定，一律当作没有缓存、走云盘直读**——这是本节最优先的一条，宁可多走一次网络，不可把上次的内容当成现状。

**可直接执行的判法**：**问自己一句——本次会话里，入口那一步跑过、并且拉到了吗？** 跑过且拉到才认；**答不上来就是没有**。这一问不必看表、也不必去查文件属性：读缓存的人和跑入口的人在**同一个上下文**里，入口这次跑没跑过是**在场事实**。上面列的那几种情形，实质都是"入口那一步这次没跑成"，这一问把它们一并覆盖。上下文被压缩时入口会**重新注入并重跑**，所以这个事实不会因压缩而失真。**一个中途被派出来的子代理并不知道入口跑没跑过**——那正是"答不上来"，按上面那条最优先的兜底当作没有缓存、走云盘直读，落在安全的一侧。

**什么时候绝对不许读它**（两条，任一命中即改走云盘直读）：

1. **看到那行失效说明**——本次会话没拉到。此时**一律改走云盘直读**。这一条已由机制兜住（旧副本已被清掉，没有东西可顶），所以真正要守的是**清空这个动作本身**：**不得为了"留着万一有用"而跳过清空、或把旧内容挪到别处存一份**。旧副本与云盘现状差了多少，本地无从知道；"反正有一份旧的，先用着"**没有合法出口**，这不是可自行权衡的取舍。
2. **要拿它当判据源**——凡用**业务事实**做判定、或据以动手的动作，一律读真相源，不因为缓存里恰好有一份就改读缓存。包括但不限于：「三、就绪判定规则」第二步与第三步的每一条（本地指针与档案版本、项目字段齐不齐、地址可不可达）、按 `合规类目` 加载哪套红线、按 `阶段` 做过滤、按档案里登记的地址往某处写入。**缓存只加速浏览，不参与任何判定，也不作为任何写入动作的地址来源。**

**为什么这一份不算"第二个维护点"**：本契约的底线是**同一个事实只有一处有人负责维护**。缓存是这条底线的唯一例外，而它能成为例外，靠下面三件事**同时**成立——缺任何一条，它立刻变成一份没人负责同步的第二真相：

1. **每次会话重拉**——每次走完入口三步，缓存或被**整体覆盖**、或被**清空**，这两种结局下**上一次的内容活不过一个会话**。还有第三种结局与两种意外，旧内容在**物理上**仍留着：**整段跳过**（曾初始化过、本地指针后来缺失或不可解析时，刷缓存不执行，既不覆盖也不清空）、入口这次根本没跑（hook 未获信任等）、清空动作自身没做成。这几种一律由上面那条**最优先的兜底**接住——「凡不确定，一律当作没有缓存、走云盘直读」，而"入口那一步这次跑过并拉到了吗"在这几种情形里恰恰答不上来。**所以旧内容在任何一条路径下都不会被当成现状**；
2. **明标只读**——**没有任何工序往缓存里写业务内容**，它只被整体覆盖、或被清空成一行失效说明。改档案、改总索引一律改云盘那一份，改完各成员下次会话自动拿到新的；
3. **真相源恒为云盘**——档案的家是云盘顶层「tingle-项目档案」，总索引的家是云盘顶层「tingle-项目索引」，缓存不是其中任何一件的家。两边不一致时**一律以云盘为准**，不存在"把本地的合并回去"这种动作。

## 三、就绪判定规则（三步）

**执行者**：三步判定引擎在**就绪 skill**（project-readiness）内**唯一实现**——全家族只此一份。**运行级 Step-0**——每个 work-skill 自带的运行前检查——只是触发：该 skill 每次运行前一行调用就绪 skill，**只判无条件前置（第二步第 1、3、4、5 条）＋该 skill 自己声明的输入与落点**（**第二步第 6 条**查 `inputs` / `outputs` 两段登记齐不齐；**第三步**只验输入的地址可达与就绪判据）；环境（第一步）归初始化入径，Step-0 不查。该 skill 声明 requirements 为空（**既无声明输入、也无声明落点**）时，第 6 条与第三步空过（记「本次无输入、无落点可判」，放行）。（**"各条全过"不是返回放行的充分条件**：`project-readiness` 在返回放行 / 返回不就绪之前，还要按它自己的「产出验收判据（DoD）」逐条过一遍收尾——本件只管判定规则，不复述那十条。）入口级的 **using-tingle 不是判定的执行者**：它只在会话开启时锚定项目维度（在哪个项目里工作）、扫描本地指针、对未初始化项目路由初始化流，不做单次运行的判定。

**判定结论与范围**：本节三步是判定的完整框架，按入径取用——**初始化入径（直呼 / 被路由）执行第一步环境＋第二步第 1–5 条**，不含第 6 条、不含第三步，不读任何技能的声明；**Step-0 入径执行无条件前置（第二步第 1、3、4、5 条）＋该 skill 自己的第 6 条与第三步**。本次入径所含各条全过 = 本次就绪，可直接运行；任一条不过 = 不就绪，转入初始化/修复，**不运行这一次**。（**这是判定的结论，不是"本次运行合格"的结论**：`project-readiness` 在宣告就绪 / 返回放行之前，还要按它自己的「产出验收判据（DoD）」逐条过一遍——本件只管判定规则，不复述那十条。）顺序不可颠倒——环境是最基础依赖，前置不成立，输入也读不了。

**就绪按人各自判**：同一个项目对甲成员就绪、对乙成员可能不就绪（装备、授权、本地指针都是个人的）。每名成员的 Step-0 在其自己的机器与自己的飞书账号下各自触发就绪 skill 判定，互不代表、互不复用结论。

**第一步·环境（仅初始化入径执行；现场查，永不落盘）**

以下各项同时成立，环境判定就绪：

1. 按**装备清单**逐项核查已装齐（清单＝lark-cli 二进制、lark-* skill 目录全套、lark-cli 授权有效**且有效的是使用者本人的 `user` 身份**，加 tingle 插件自身已装）。**这份清单写死在 `tingle-core` 里，由维护者手工维护**——不扫描各 skill 的声明、不自动扩展（2026-08-17 定；此前写着"随其 requirements 声明进清单"，而声明格式里从来就没有一格能装"我需要机器上装什么"，那句承诺从写下那天起就落不了地）。**新依赖怎么进来**：某个 skill 真正开跑时发现它需要的东西没装，把这个依赖提给维护者、加进插件层级那份清单，随下一版发出去。其中 **lark 全套为必查最小集**，机械核查法：`command -v lark-cli` 有输出；`~/.claude/skills/lark-*` 或 `~/.agents/skills/lark-*` 路径下存在 lark 相关 skill 目录；
2. **`lark-cli` 授权有效，且有效的必须是使用者本人的 `user` 身份**——判法见紧随其后的「授权判据：只认 `user` 身份，三态判定」。

任一项不成立，环境判定未就绪；不必再看第二步，先补装/授权。技能运行前（Step-0）不查环境；运行中环境失效＝出了问题检查配置修掉，执行 AI 按报错性质自行判断处置。

**授权判据：只认 `user` 身份，三态判定**

跑 `lark-cli auth status`（只读命令），按下面两问判。

**第一问 · 认哪个身份：只认 `user`。** 这条命令返回的是**两套并列的身份状态**——应用身份（`bot`）一套、使用者本人身份（`user`）一套，**没有一个代表整体的总状态字段**。所以判据只看 `user` 那一套：`bot` 是不是 ready 与本判据无关，"有一个身份是 ready 的"也不构成通过。**返回顶层若有一个标着默认身份的字段（写作本件时是 `identity`），那是"默认用哪个身份发请求"的设置、不是状态**，它写着 `user` 不代表 `user` 的授权还活着——不得据此判过。

**为什么必须是 `user`（这条理由不可省，它决定了判错的代价）**：本体系记录「谁产出的」不靠专门字段，靠的是**写入飞书时留下的创建人元数据即为本人**——多名成员共写同一处飞书落点时，「这一行是谁写的」全靠它。若 `user` 授权已经失效、只有 `bot` 还活着，而判据放了行，此后所有飞书写入都会以**应用身份**落地——表照建、行照写、字段照填，**不报任何错**，但每一条记录的创建人都变成了这个应用。多人协同赖以成立的经手人追溯就此整体失效，且是**无声失效**：要等到有人来查"这几行是谁写的"才会发现，那时已经分不清，也无法回溯补救。所以这一条判的不是"能不能连上飞书"，而是"写进去的东西还认不认得出人"。

**第二问 · `user` 这一套处在三态中的哪一态**（**"需刷新"是常态，不是故障**）：

| 态 | 语义 | 动作 |
|---|---|---|
| ① 可直接用 | `user` 身份在场，且授权仍在有效期内 | **过** |
| ② 已过期、但可自动续 | access token 已过期，而 refresh 的有效期**尚未到** | **先刷新，成功即过**——刷法见下 |
| ③ 连 refresh 也过期 | refresh 的有效期也已过，续不回来 | **不过**，转装备补齐，由使用者本人重新走一次完整授权 |

**② 是日常路径，不是异常分支**：实测 access token **数小时**即过期、refresh 撑**约一周**。也就是说，凡隔几个小时再开工的会话，遇到的几乎都是 ②。把它当成"授权坏了"去惊动使用者，是把最常见的一种情况当成事故。

**② 的刷新怎么做**：依赖 `lark-cli` **在下一次 API 调用时自动续期**——跑一条**只读**的用户身份命令即可触发（例如再查一次状态，或读一个已知可读的资源），续上即视为通过、继续往下走。**不得改跑 `lark-cli auth login`**：那是走一整套重新授权流程，会平白打断使用者做一次本不必做的完整授权；`auth login` 只属于 ③。

**字段路径与取值都只作示例，语义才是判据**：写作本件时，上述三态在返回里的对应位置是 `identities.user.available`（`user` 身份是否在场）、`identities.user.tokenStatus`（当前 token 状态）、`identities.user.expiresAt` 与 `identities.user.refreshExpiresAt`（两个有效期）。**这些路径随 `lark-cli` 版本可能变**——实际返回对不上时，按上面两问的**语义**重新判（哪一套是使用者本人的、它的授权还在不在有效期内、refresh 的有效期到没到），**不要照着这里的路径猜一个相近的字段**，也不得因为路径对不上就把这一条跳过去。**取值同样只作示例**：真机上观测到过 `valid`（＝上表的 ①）与 `needs_refresh`（＝②）两个值，但**这套取值没有任何公开的枚举承诺**——它随 `lark-cli` 版本走，今天见到的两个不代表全集（例如授权被使用者在后台解除时会是什么值，就不在这两个之内）。所以**判据不得写成"与某个字面值相等才算过"**——按有效期语义判，别跟字面值较劲；**反过来，遇到一个不认识的取值，也不要当成"没见过就等于没问题"放过去**，那种情况按"判不准则不放行"处理，转 ③。

**第二步·本地指针与档案**

按顺序核查，以下各项同时成立才通过：

1. **本地指针在**：当前项目工作文件夹下 `.tingle/state.json` 存在，且 `tingle_state_version`、`profile_link`、`initialized_at` 三字段齐全非空；
2. **本地指针版本匹配**：`tingle_state_version` 值等于 **2**（当前契约本地指针版本）；
3. **档案打得开**：以 lark-doc 打开 `profile_link` 指向的文档，能读取正文中的 JSON 代码块并成功解析；
4. **档案版本匹配**：档案 `tingle_profile_version` 值等于 **2**（当前契约档案版本）；
5. **档案项目字段齐**：`project.id`、`project.name` 存在且非空；`project.tags.品类` 下三级（`业务线`/`合规类目`/`产品品类`）均存在且非空；`project.tags.品牌` 存在且非空；`project.阶段` 存在且非空；**顶层 `folder_token` 存在且非空**；项目级 `initialized_at` 字段存在；
6. **目标 skill 输入与落点齐**：本次要运行的 skill（按其名字）在档案 `skills` 段下有对应键，且**两段都齐**——① 该键 `inputs` 下，它 requirements 里**声明的每一个输入**都在且字段齐全；② 该键 `outputs` 下，它 requirements 里**声明的每一个落点**都在且字段齐全。两段的"齐"同一标准：`type` 有值，且按 `type` 对应的值字段有值（`lark-doc` → `link`；`lark-base` → `base_token`+`table_id`；`lark-drive` → `folder_token`）。**声明里没有的不查**——`requirements.outputs` 为空的 skill，本条只看 `inputs`。**本条查的是"登记齐不齐"**（有没有这一项、`type` 与值字段全不全）；**地址可不可达不在本条**——那在第三步，而第三步只验 `inputs`。**声明了落点却没在档案里登记＝不就绪、本次不跑**：落点和输入一样是运行前提，放它先跑等于把"写哪儿"推到活已干完、正找地方放的那一刻。

任一项不成立，判定不就绪：第 2 条（本地指针版本不匹配）→ **路由初始化重建本地指针**；第 4 条（档案版本不匹配）→ **路由初始化迁移档案**——就地覆盖这一份，不新建（两者均见「二、本地指针模板」的「版本字段与不匹配处理」，迁移动作见其下「档案 1 → 2 的迁移动作」）；第 6 条（仅 Step-0 入径执行）分两支——**输入缺** → 按 `produced_by` 路由生产者重产，无 `produced_by` 则交人修复（见第三步末与「四、requirements 声明格式」`produced_by` 条）；**落点未登记** → 走道10 补登记（写档案、先放行，**地址只能是使用者在放行清单里给出的那一个，不自行选址**），登记完复验本条，过了才跑这一次——`produced_by` 是 `inputs` 段专有的格，落点没有生产者可路由；其余各条 → 路由初始化补齐。

**第三步·验（仅 Step-0 入径执行；地址可达 + 就绪判据）**

对发起调用的那个 skill 在档案 `skills.<skill_name>.inputs` 下记录的**每一个输入**（只此一个 skill，不及其他；`outputs` 是产出落点，**登记齐不齐已由第二步第 6 条管住**，其地址可达性不在本步范围——真写不进去时按报错性质当场处置），逐个执行以下两项：

1. **地址当场打得开**：按 `type` 对该地址轻量访问一次——`lark-doc` 读取文档标题、`lark-base` 读取表的基本信息、`lark-drive` 列出文件夹——访问成功即通过。链接失效、资源被删、**当前成员权限不足**都在此项暴露：成员飞书账号对项目资源的访问权这一前置检查项，即在此步自然覆盖；
2. ~~**就绪判据逐条过**~~ —— **本步已于 2026-08-17 移出判定**。程序不读「就绪判据」这一格，它只做上面第 1 项（地址打不打得开）。判据原样附在开工单上，由**发起这次运行的那个 skill 在开跑时自己逐条对照判**（见「四、requirements 声明格式」`就绪判据` 条）。
   **改这一条的理由**：判据写成中文句，同一格里躺着两类完全不同的东西——「表里存在今天日期的记录」程序跑得了，「写明角标由哪几个成分组成」必须读内容才判得了，而**程序无法凭格式区分它们**。全交给程序，程序会撞上一堆执行不了的句子。分工改成：**机械事实归程序，内容合不合用归 AI 运行时判。**

任一输入任一项不过，判定不就绪，转入修复：地址失效 → 更新档案中对应配置；判据不过且该输入标有 `produced_by` → 修复路由指向该生产者 skill 重产此输入（见「四、requirements 声明格式」）；无 `produced_by` 的输入 → 交人修复——该输入是这个 skill 自己的运行前提，**其来源**随该功能自己的接口定。

**同一个输入，调过生产者之后仍不过 → 停，不再重试。** 生产者跑完后复验该输入，判据仍不过时立刻停下，**不做第二次回调**——同样的调用第二遍不会有不同结果，只会一圈圈转，而且转得无声无息。停时报出四样：① 这个输入的名字；② 调了哪个生产者；③ 该生产者报的完成状态；④ 一句诊断——「生产者跑完了但这件仍缺，很可能它不在该生产者的产出清单里：名字不符 / 尚未接入 / 模板未就位」。**真正的修法交人**：把那件东西接进生产者的产出清单与物料 IO 表，或改正声明里的输入名。就绪 skill 只负责把卡点报清楚，不替人猜、不反复重试。

## 四、requirements 声明格式

任何新 skill 接入 tingle 就绪系统 = 在自己 SKILL.md 里按本节格式声明一段 + 项目初始化/补齐时在该项目**项目档案**的 `skills` 段按声明多登记一块，本件主体不改。

每个 skill 在自己的 SKILL.md 里声明的 `requirements`，是项目档案里 `skills.<skill_name>` 那一层结构的**"只留类型与判据、不留值"版**——**同样分 `inputs` / `outputs` 两段**，两段的键与档案里那两段一一对应：`inputs` 说明"这个 skill 需要读哪些东西、各是什么类型、内容达到什么状态才算可用、由谁生产"，`outputs` 说明"这个 skill 要往哪几类落点写、各是什么类型"。值（具体链接/token）由项目档案负责填。

**格式**：

```json
{
  "requirements": {
    "inputs": {
      "<input_name>": {
        "type": "lark-doc",
        "就绪判据": ["<内容级可判中文句>", "<可多条，逐条可判>"],
        "produced_by": "<生产该输入的 skill 名>"
      },
      "<input_name_2>": { "type": "lark-base" },
      "<input_name_3>": { "type": "lark-drive" },
      "<每次跑都是另一份的那样东西>": {
        "每次输入不一样": true,
        "就绪判据": ["<开跑时自己对照判的条件>"]
      }
    },
    "outputs": {
      "<落点名>": { "type": "lark-base" },
      "<落点名_2>": { "type": "lark-drive" }
    }
  }
}
```

两段都可为空（无输入写 `"inputs": {}` 或整段不写，无产出落点同理）；**声明 requirements 为空**即两段皆空。

`type` 在两段都为必填，取值集同为 `lark-doc` / `lark-base` / `lark-drive` 三值。**「`就绪判据`」与 `produced_by` 是 `inputs` 段专有的两个可选格**——`outputs` 段每项只声明 `type`：落点是本 skill 自己要写的地方，没有别的生产者可路由，其内容状态也不是本 skill 的运行前提。规则如下：

- **`就绪判据`（可选）**：值为一条或多条**内容级可判中文句**的列表——每句描述"这项输入的内容处于可用状态"的一个检验条件，且可当场判成立/不成立（如"某八个字段段落齐""存在运行当天采集的记录"）。判据只写**内容级**条件（字段齐不齐、记录新不新、结构对不对），不写环境或权限条件——那分别归装备检查与地址探活，不在判据里重复。

  **谁来验：AI，不是程序**（2026-08-17 定，此前写的是程序逐条验）。`tingle check` **一概不读这一格**——它只判「登记齐不齐、地址打不打得开」这类机械事实。判据原样附在开工单上，由**发起这次运行的那个 skill 在真正开跑时逐条对照判**。

  **正因为改由 AI 判，这一格更要写清楚，不是更可以含糊。** 程序有个天然兜底：遇到它执行不了的句子会报错，你至少知道出事了；换成 AI 判，这个兜底没了——判据写得含糊，它会自己挑一个解释放过去，**而且不报任何症状**。所以规矩不变：**每条都要能当场判成立或不成立**，写不成这样的不许写进这一格，改写进该 skill 自己的运行纪律。判不准时**停下问人**，不许挑一个解释混过去。

- **`每次输入不一样`（可选，布尔）**：标 `true` 表示这一样**每次跑都是另一份**——同一个项目里每次都不同，也不是跨项目共用的那一份（例如某次要校对的那篇稿子、造 skill 时喂进去的那份做法材料）。这类输入**不登记在项目档案里**，所以 `tingle check` 不去档案找它的地址、也不探活，只在开工单上记一行提醒「这一样运行时给」。它**不写 `type`**（形态不固定，本地文件／云文档／云盘文件都可能）；`就绪判据` 照写，那是开跑时自己要对照的。
  （2026-08-17 新增。此前输入只分「随项目变」「跨项目同一份」两类，装不下这第三类——后果是同一个月造出的两个 skill 对同一类东西给了两种互不相容的答案，两个都通过了独立评审，因为没有一条规矩说该往哪走。）
- **`produced_by`（可选）**：值为**生产该输入的 skill 名**（如蒸馏产物之于 `context-distill`）。作用是**修复路由**——当该输入缺失或判据不过时，就绪 skill 据此给出"调 `<produced_by>` 重产此输入"的修复指向；**该指向只走一次**——调过生产者后该输入仍不过，就绪 skill 停、不再重试，改为报卡点（输入名＋调了哪个生产者＋其完成状态＋诊断）交人修（见「三、就绪判定规则」第三步）。**无 skill 生产者的输入不标**（如人工配置的表、外部数据底座供给的表）；不标者缺失时交人修复——缺的若是项目或人的地基（本地指针、档案、项目字段），才路由初始化。

**与项目档案的对应关系**（同一套字段，一边记类型与判据、一边记值）：

| 位置 | 记什么 | 出现的字段 |
|---|---|---|
| SKILL.md 的 `requirements.inputs.<input_name>` | 这个 skill **需要**的输入：类型 + 内容级判据 + 生产者 | `type`（取值 `lark-doc` / `lark-base` / `lark-drive`）、`就绪判据`（可选）、`produced_by`（可选） |
| 项目档案的 `skills.<skill_name>.inputs.<input_name>` | 这个项目**已配好**的输入值 | `type` 相同 + 按 type 对应的值字段：`lark-doc` → `link`；`lark-base` → `base_token`+`table_id`；`lark-drive` → `folder_token` |
| SKILL.md 的 `requirements.outputs.<落点名>` | 这个 skill **要写到**的落点：只有类型 | `type`（同一取值集） |
| 项目档案的 `skills.<skill_name>.outputs.<落点名>` | 这个项目**已批准**的落点值 | `type` 相同 + 按 type 对应的值字段（同上） |

两侧共享同一套键名空间（`inputs` 下的 `<input_name>`、`outputs` 下的 `<落点名>`）与同一个 `type` 取值集合——requirements 只声明"要什么类型、内容达标线在哪、谁产的、往哪类落点写"，不出现 `link`/`base_token`/`table_id`/`folder_token` 这些值字段（那是项目档案的职责）；项目档案只记值，不出现 `就绪判据`/`produced_by`（那是 requirements 的职责）。**就绪 skill**（由运行级 Step-0 一行调用）判定"该 skill 的**输入与落点**是否齐全"时，正是拿 requirements **两段**里声明的键逐一去项目档案的对应两段下核对是否存在、且按其 `type` 对应的值字段齐全——`inputs` 对 `skills.<skill_name>.inputs`，`outputs` 对 `skills.<skill_name>.outputs`（即「三、就绪判定规则」第二步第 6 条）；随后**只对输入**验地址可达并逐条过其声明的就绪判据（即「三、就绪判定规则」第三步——**落点不验地址可达**）。**`outputs` 两侧只做登记与对照、不设内容判据**：档案里登记的就是本项目批准给该 skill 的落点，skill 照此取用、不自行选址。**但"不设内容判据"不等于"不查"**——**登记齐不齐照样归第 6 条管**：声明了落点却没在档案里登记＝不就绪、本次不跑。

## 五、多人运行原则

一个项目多名成员共用时，按以下原则运行：

- **N 本地指针 1 档案**：一个项目 N 名成员 = **N 份本地指针 + 1 份档案**。档案是项目共享真相，全员共读共用同一份；本地指针是个人的，各自落在自己机器上。项目云盘地址与各 skill 的输入、输出地址都只记在档案一处——地址变更只改档案，各成员下次运行自动获得新地址。成员加入已初始化的项目时，只做个人级工序（装备预装、权限、写本地指针指向档案），项目级全部跳过——读到档案即知该项目已初始化。
- **就绪按人各自判**：同一个项目对甲成员就绪、对乙成员可能不就绪（装备、授权、本地指针都是个人的）。每名成员在自己的机器与自己的飞书账号下各自触发就绪判定，互不代表、互不复用结论。
- **本地指针每人一份**：不存在全局共享的本地指针，也不存在按项目 ID 索引的集中本地指针库；每名成员的本地指针就是自己项目工作文件夹下的 `.tingle/state.json`。
