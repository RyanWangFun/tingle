# Tingle

**Tingle 是 AI 营销操盘大脑——让 AI 当项目的操盘者**，装载项目全部资料与决策记录，覆盖策略制定、执行、复盘、迭代、再策划全流程。客户服务、策划、媒介、投流四条线在同一个大脑上工作：共用同一份项目上下文，各环节的判断互相衔接、对得上同一个 KPI。人负责拍板，大脑供依据、选项与执行。

**它以插件为载体**，装在 Claude Code（与 Codex）里，**每台机器装一次**，此后任何客户项目、任何成员都能跑。

**它会长大**：插件名称固定为 `tingle`，往后新增的能力都归入同一个插件，无需重新安装或更改安装命令；**每个项目跑出来的经验与方法论沉淀回插件，所有项目即时复用，越用越强。**

## 前置依赖 / Requirements

**先配好前置依赖，再装插件。** 本插件内的 skill 依赖 lark 工具链读写飞书：

- 安装 `lark-cli`（`larksuite/cli`）：在系统终端跑 `npx skills add larksuite/cli -g`——这一步同时把 `lark-*` 系列 skill（`lark-doc` / `lark-base` / `lark-drive` 等）装到位，插件内的 skill 全靠它们读写飞书，缺了就跑不动
- 执行 `lark-cli auth login` 完成飞书授权，并保持授权有效（授权走你本人的飞书身份，过期了重跑一次）
- 拥有该项目飞书云盘文件夹的访问权——材料、蒸出来的项目上下文、项目档案、项目总索引都落在那里

另有两条与运行环境有关：

- **Node.js**：上面装 `lark-cli` 用的 `npx` 由它提供，没装先去 [nodejs.org](https://nodejs.org/) 装一个。macOS 与 Windows 都需要。
- **Windows 用户另需安装 [Git for Windows](https://git-scm.com/download/win)**（装的时候会一并装上 Git Bash）。本插件的会话入口靠一个 shell 脚本在会话开始时注入，Windows 上要有 Git Bash 才跑得起来；没装的话插件其余部分照常可用，只是每次会话开始时入口不会自动到场——那时在对话里直接说「使用 using-tingle」可手动加载。macOS 自带，无需安装。

## 安装

> 说明：`/plugin …` 是在 **Claude Code 对话框里**输入的斜杠命令（不是系统终端）；`npx` 是在**系统终端**里跑。

### Claude Code

在 Claude Code 会话里依次输入：

```
/plugin marketplace add RyanWangFun/tingle
/plugin install tingle@tingle
/reload-plugins
```

装好后即可使用。会话入口随会话自动加载，其余 skill 都是 model-invoked 技能，Claude 会按任务自动调用（如需显式调用，名为 `/tingle:<skill 名>`，如 `/tingle:project-readiness`）。

### Codex

Codex 支持从 GitHub 加载**插件市场**。在 Codex 的「插件 → 添加插件市场」对话框里填：

- 来源：`RyanWangFun/tingle`
- Git 引用：`main`（主分支）
- 稀疏路径：留空

或用命令行：

```
codex plugin marketplace add RyanWangFun/tingle
```

添加市场后，在插件列表里安装 `tingle`。新装插件 Codex 会自动发现，没出现就重启 Codex。

## 双侧差异（Claude Code vs Codex）

tingle 的会话入口（using-tingle）经 SessionStart hook 随会话自动注入，两侧共用同一份 hook 文件，无需分别配置。Claude Code 装完即用；Codex 多两步，都只做一次。

**第一步：信任本插件的 hook。** Codex 装好或启用插件后，插件自带的 hook 不会立刻生效——按 Codex 官方文档，插件捆绑的 hook 属于非托管 hook，须由你审核并信任后才运行（Claude Code 无此步骤）。在 Codex 里用 `/hooks` 查看并信任即可。

要点：**信任是按 hook 定义的内容记录的**，所以插件更新一旦改动了 hook 定义，它会重新变回待审核状态、hook 被跳过，届时再用 `/hooks` 信任一次即可（0.4.1 就改动了 hook 定义，从更早版本升上来的话请重新信任）。信任生效前，在对话里直接说「使用 using-tingle」可手动加载入口。

**第二步（仅当 `/hooks` 里根本看不到本插件的 hook 时）：手动登记一次。** 看不到说明你这个 Codex 版本尚未开启"自动发现插件自带 hook"的能力（该能力在 Codex 中曾置于特性开关之后）。这时把下面这段加进 `~/.codex/hooks.json`，效果完全相同——本插件的 hook 脚本会自行推导插件位置、不依赖任何环境变量，所以按绝对路径调用照样工作：

```json
{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup|resume|clear|compact",
        "hooks": [
          {
            "type": "command",
            "command": "\"<插件安装路径>/hooks/run-hook.cmd\" session-start",
            "shell": "bash",
            "timeout": 10,
            "additionalContextLimit": 0
          }
        ]
      }
    ]
  }
}
```

`<插件安装路径>` 换成本插件在你机器上的实际位置。不确定装在哪，在终端跑这条即可查出 `run-hook.cmd` 的完整路径，把上面那行里的 `<插件安装路径>/hooks/run-hook.cmd` 整段换成它（外面那对双引号留着）：

```bash
find ~/.codex -name run-hook.cmd -path '*tingle*' 2>/dev/null
```

加完同样需要用 `/hooks` 信任一次。

**关于注入长度**：Codex 对 hook 注入内容默认有约 2,500 token 的上限，超出部分不会被截断，而是被存进临时文件、只给模型一段头尾预览加文件路径——对入口来说这比截断更糟，模型多半不会去读那个文件。本插件的 hook 已声明 `additionalContextLimit: 0`（完整内容原样交给模型），所以入口全文总是完整到场，改动入口内容时也无需再核算长度。**这个字段不要删。**

## 0.9.0 新增：全链路十件工作 skill，以及一类新的 skill

**这一版之前，插件基本是地基**——把项目弄到能干活，加三件交付前的核查。**这一版起，一单生意从头到尾每一站都有人管了。**

### 一、营销全链路十件

一单生意的完整路径，一站一件：

> 读 brief → 定策划与指标 → 定人群 → 挖需求 → 选内容方向 → 造成片 → 配投放 → 接住搜索 → 卖货 → 复盘

每一件的形状都一样：开工前自己跑一次前提检查（缺东西就说卡在哪、不硬跑），几道按序走的工序，声明清楚它读什么、写到哪、哪一步不许自动、什么情况必须停下来交人，最后一份能逐条对着判的验收标准。**它们不替你拍板**——凡是决定项目走向的那几步，产出都要你过目才算数。

### 二、方法 skill——一类新东西

前面十件回答的是「这一趟怎么走」。但有些道理是**横切的**：好几个环节都要用同一套判断，比如"这算不算一个真问题""一条内容由哪些要素构成""什么样的经验才值得留给下一单""每个数字挂不挂得回一段意图"。

这类道理如果抄进每个用到它的 skill，改一处就要改好几处，时间一长必然各说各的。所以它们单独成一类，**不对应任何一站、不独立运行**，由用到它的 skill 在该用的时候加载：

- **validating-the-real-problem（验真问题）**——把一句模糊命题或一个表象，验成一句可衡量的真问题并追到根因。读 brief 时用，复盘时也用，是同一套方法。
- **elementizing-content（内容要素化）**——把一坨内容拆成能单独打磨、能重新拼装的要素，定位它们，找出短板。**两个方向**：拆没跑起来的是找短板，拆已经跑赢的是把还能再用的那几样取走。
- **banking-proven-assets（经验沉淀判准）**——判一批跑出来的东西够不够格留给下一单、沉进哪一格、成色算哪一档。**十件工作 skill 全都用它**。
- **keeping-metrics-anchored（定性定量对齐）**——每个数字必须说得清它在证明哪段策略，每段策略必须有数在量它。防的是"指标全绿、结果没来"。

### 三、由此接上的那个闭环

一单跑完 → 复盘把跑赢的几条拆成要素、判出哪几项还能再用 → 交给沉淀判准判够不够格 → 沉进对应的格子并标明成色 → **下一单开工直接调料，起点比这一单高。**

两道闸不重叠：前者判**形态上**能不能复用（能不能单独抠出来装到别的内容上），后者判**证据上**够不够格（验过没有、验了几次）。都要过。

### 四、常驻件里装进了判断的立场

到 0.8.2 为止，每个项目文件夹里那段常驻件写的全是**操作规矩**——先跑检查、程序判机械事实、写飞书前摆清单、不编造。读完它，AI 知道怎么使唤这套工具，却不知道该拿什么尺子看业务。这一版把立场补上，常驻件现在还带三样：

- **你站在哪儿** —— 项目总操盘位，不是某一道工序。策略、人群、内容、选号、投放、客户沟通、复盘在同一条链上，每个判断都要接得住上游、喂得了下游，各条线对同一个 KPI。
- **四条公理** —— 看能不能卖掉不看做得好不好；交付的是判断不是工时；确定性是设计出来的；单次做成不算数、能复用才算数。它们不是某个环节的方法，是全部判断的方向。
- **每个判断当场记三样** —— 判断、依据、赌注。赌注最容易漏也最要紧：只记判断和依据是一份完整的记录，却产不出认知，数据回来时没有清算对象。

**你手上那份不会自动变。** 常驻件带结构版本号，这次从 1 升到 2；升级插件后，`tingle resolve` 会告诉你本机这份是旧的，按它的指引跑一次就换成新的（标记区外你自己写的内容一字不动，覆盖前存备份）。

### 五、装了这一版要做的事

1. **升级插件**（Claude Code 里 `/plugin marketplace update tingle` 后重装，或按下方安装步骤重跑一遍）。
2. **每个在用的项目各跑一次 `tingle resolve`** —— 它会报常驻件结构旧，照它说的做一次就好。
3. 新增的 skill **不用配置**，Claude 会按任务自己调；想显式点名就用 `/tingle:<skill 名>`。

## 0.8.2 新增：两个审核类工作 skill

内容做出来之后、交出去之前的那两道关，现在各有一个 skill 管。

**一、check-draft-compliance（稿件送审前核查）** —— 稿子写完、送客户或送内部审核之前先过一遍：哪一处说了本项目不许说的、哪一处跟产品资料对不上、该带的要素和限定语齐不齐、内容有没有放错栏位。每一处判有问题的都给**可直接替换的原句**，不给"建议优化表述"这类没法执行的话。

**二、check-cut-against-baseline（成片交付前核对）** —— 片子剪完、交出去之前逐时点核：口播有没有改词漏词、限定语被剪掉没有、该露出的元素够不够早、必须常驻的标识在片尾丢没丢、字幕有没有错字或断错句、外部与合成素材的标识漏没漏。每条带时间定位和具体改法；也支持"上一轮反馈改了没有"这种逐条闭环复核。

两件都**不替你做决定**：判为"可以送出去"的那一档必须你点头；而它们只判、不改——改稿和重剪都是人的活。详见下方 skill 清单。

## 0.8.0 新增：第一个干活的 skill，以及常驻件

**一、check-claim-citations（文献引用校对）** —— 插件到 0.7.0 为止都是"把项目弄到能干活"的地基，没有一件是直接干活的。0.8.0 装进第一个：给一份已成稿的内容稿做引用校对，逐句判哪些话需要证据、配到证据上、按稿内首次出现重编号，最后**把角标与文末条目落进稿件的副本**，交出一份可以直接送审的成品稿，外加一份供复核的校对结论。详见下方 skill 清单。

**二、常驻件** —— 每个项目工作文件夹里，`CLAUDE.md` 与 `AGENTS.md` 现在会各有一小段 tingle 写的正文（在 `<!-- tingle:常驻件 -->` 标记之间）。它装的是干活的规矩——开工前先跑检查、程序只判机械事实、写飞书前先摆清单等你放行、材料里没有的不编造。**你不用管它**：初始化时自动写入，随插件升级自动更新，`tingle resolve` 会在它缺失或过期时报出来。

- **只动标记之间**：标记区外你自己写的任何内容一字不动，覆盖前还会存一份备份。
- **两侧都铺**：`CLAUDE.md` 管 Claude Code，`AGENTS.md` 管 Codex。只铺一侧的话，用另一侧的同事就静默拿不到这段正文。
- **区内你改过的东西不会被无声抹掉**：重建时会把改动摆出来给你看——有人在这儿手写了东西，通常意味着那段内容该被正式收编。

## 0.7.0 新增：检查改由程序做

0.7.0 起，插件带一个确定性核心 `tingle-core`——**原本写在文档里、靠 AI 自己读着执行的那套检查，现在是真程序**。它管全部"机械事实"的判定，跑一次吐几行结果。

**你不用配置它，也不用记路径。** 它随插件一起装上，会话一开始就把自己的位置告诉 AI，各 skill 会在该跑的时候自己跑它。（它**不装进你的 PATH**——不改你的环境、不加安装步骤，所以终端里直接敲 `tingle` 是没有的；想自己敲就问一句 AI「tingle 程序在哪」，它会给你完整路径。）

它一共五条命令：

| 命令 | 它回答什么 |
|---|---|
| `tingle doctor` | 这台电脑装齐了没有（飞书命令行工具、授权、插件自身） |
| `tingle resolve` | 这个项目在这台电脑上能不能直接开工 |
| `tingle refresh` | 把项目档案与项目总索引拉一份到本机，供快速浏览 |
| `tingle migrate` | 结构过时了，就地升级（本机的直接改；要写飞书的先给你看清单，你放行才动） |
| `tingle check <skill 名>` | 这个 skill 这一次能不能跑；能就给开工单，不能就说卡在哪、谁能补 |

`tingle resolve` 的回答只有五种：**正常 / 本机未配置 / 配置不完整 / 结构旧 / 打不开**。看到「打不开」别当成「没配过」——前者是访问不了（找权限或重试），后者是没配过（要走初始化），修法完全不同。

**一条边界值得记住**：程序只判「东西在不在、打不打得开、版本对不对、登记齐不齐」。至于**内容够不够用**（这份资料写全了没有、结构对不对），程序一概不判——那由 AI 在真正干活时逐条对照判，判不准会停下来问你。

**要装的东西怎么进这份清单**：`tingle doctor` 查的是一份写死在插件里的清单，由维护者维护。某个 skill 跑起来发现还缺什么要装的，提给维护者加进去、随下一版发出来；它不会自动扫描各 skill 去发现新依赖。

## 含哪些 skill

共 21 件，分三类：**平台**四件（让项目跑起来）、**工作**十三件（链上一站一件）、**方法**四件（横切多个环节的判准，不独立运行）。

### 平台四件

- **using-tingle（会话入口）**：每次会话开始时自动加载（无需你调用），确认当前在哪个项目里工作、这个项目在你机器上初始化过没有；没初始化过就把你带到初始化那一步。它管到这里为止——之后每次干活前的前提检查不归它，归下面的 project-readiness。
- **project-readiness（项目就绪）**：本插件的就绪总管。① 各 skill 运行前由它检查这一次的前提齐不齐（缺则说明卡在哪、不让这次跑）；② 也可以直接对它说「把这个项目弄就绪」，它会带你把一个新项目从零配齐——建云盘落点、打标签、标明项目走到哪个阶段、收料、把材料整理成 AI 读得了的形态、蒸出项目上下文，最后写项目档案和一份项目总索引（这个项目有哪几类东西、每类从哪儿进）。凡要写飞书的动作都会先停下来等你放行。
- **context-distill（项目材料蒸馏）**：把散在各处的项目材料收拢上飞书云盘，转成 AI 读得了的形态，再蒸馏成全家族共用的项目上下文——每一条都能回溯到是从哪份原材料来的；材料更新后就地重蒸，不推倒重来。
  **它不只产那一整套**（0.6.0 起）：你也可以给它一份"要产成什么样"的规格，让它**照规格只产其中一件**——例如某个 skill 专门要吃的那份输入件。规格通常就是那个 skill 自己声明的"这份东西要写明哪几样"，不必另写一份。产出同样逐条溯源、同样先交人过目。

前三件合起来是一套**项目初始化基础设施**——把一个客户项目在你自己机器上从零弄到能干活。初始化完成的标准是「地基齐」（云盘落点、材料、项目上下文、项目档案、项目总索引、本地指针），不以任何具体业务技能就绪为准。

- **building-work-skill（把做法造成 skill）**（0.5.0 新增）：你手上有一套已经在用的做法——可能是口述的、一份工作流走查纪要，或者一个自己攒的自用件——它带你把这套做法变成别人也能装上就用的 skill。逐道过五关：这个 skill 到底管哪一段（别一个 skill 塞两件事）、哪些规则该外置到哪一层（别把某个客户的规矩焊死在正文里）、用到的每样东西从哪儿来（别留下"运行时自然就有"的悬空）、哪几步不许自动、得停下来让人判、以及怎么测它。

  它跟上面三件的关系：那三件负责**把项目弄到能干活**，这一件负责**把你的做法变成能复用的工具**。两边独立，不必按顺序用。

### 工作十三件 · 营销全链路十件（0.9.0 新增）

按一单生意的顺序排，每一件吃上一件的产出：

| # | skill | 它交出什么 |
|---|---|---|
| 1 | **decoding-client-brief**（读 brief） | 把一份客户 brief 拆成团队明天能动手的方案框架，并交代它凭什么这么拆 |
| 2 | **planning-campaign-and-kpi**（定策划与指标） | 一份能对外承诺的投放策划，含它撑得起的那组指标，以及这组数凭什么成立 |
| 3 | **mapping-target-audiences**（定人群） | 把一个产品转译成一张排好序、配好触达语言的人群表 |
| 4 | **mining-user-needs**（挖需求） | 把每类人身上的真需求挖出来，并翻译成他自己会说的那句话 |
| 5 | **choosing-content-angles**（选内容方向） | 把每条需求落成一个具体的内容方向，并为它选定一种内容形态 |
| 6 | **producing-content-pieces**（造成片） | 把一条已定的内容方向做成一条可投的成片 |
| 7 | **configuring-media-buying**（配投放） | 一份投放方案，并让它持续跑在效率线上 |
| 8 | **capturing-search-demand**（接住搜索） | 把被种草的人在他回搜的那一刻接住并转化 |
| 9 | **converting-traffic-to-sales**（卖货） | 把承接来的流量变成一门算得清、能放量的生意 |
| 10 | **reviewing-campaign-results**（复盘） | 把数据归因到根因，并把它沉淀成下一单能直接用的东西 |

**每一件都不替你拍板**：决定项目走向的那几步，产出要你过目才算数；碰到红线不确定、缺关键事实、或要对外发送，它会停下来交给你。

### 工作十三件 · 交付前核查三件

- **check-claim-citations（文献引用校对）**（0.8.0 新增）：一份成稿要送审或对外发布之前，先过一轮引用校对。它逐句判哪一句会被人追问出处、到本项目的证据索引里配对、按稿内首次出现重新编号，然后在**稿件的副本上**把角标和文末条目标好，交出成品稿；原稿一字不动，两份可以并排对照。
  它有两处会停下来等你：抽完稿件结构后请你确认没有漏抽、出成品之前请你过目判定表——**没有你点头就没有成品**。另外，"证据原文里有这句话"不等于"这条证据可以引"，凡是缺获批凭证的它只标「待确认」、不会替你生成一个看起来很正常的角标。
  **它要读的三样东西随项目走**：本项目的证据索引表、证据原文库、以及一份写明"哪几类话须有出处、引成什么样、有哪些豁免"的说明。没配齐时它不会硬跑，会告诉你缺哪一样、谁能补。

- **check-draft-compliance（稿件送审前核查）**（0.8.2 新增）：一份还没发出去的稿——口播脚本、投放文案、笔记稿都算——在送客户或送内部审核之前先过一遍。它把稿子按栏位拆成可指着说的一处一处，每一处按四件事各判一遍：说了不该说的没有、说的跟产品资料对不对得上、该带的要素和限定语齐不齐、内容有没有放错栏位。**每一处都留痕，包括判"没问题"的**——只列有问题的那几处，漏判和"这处没问题"在清单里长得一模一样。判有问题的每一处都给可直接替换的原句。
  它**只判、不改稿**：改法是建议，落不落进稿子是写稿人的决定。判为"可以送审"的那一档要你点头才算数。
  **要读的三样东西随项目走**：本项目的表述禁令材料、产品资料、以及一份写明"一份稿分哪几栏、必须出现什么、字数怎么算"的说明。

- **check-cut-against-baseline（成片交付前核对）**（0.8.2 新增）：一条剪好的片子在交出去之前，拿本次的基准（定下来的那一版稿，或上一轮的修改意见清单）逐时点核一遍。先把基准抽全（脚本正文常整段躺在表格里，只读段落会漏掉整块口播），再分层抽帧取证，然后两维核对：对不对得上基准、守没守住本项目的制作规矩。
  **不符项和通过项一起交**——只列问题，制作方就不知道哪些不必返工。看不清的地方它会回原始清晰度重取，仍判不准就写"需人工复核"，**不猜**。判为"可提交"的那一档要你点头。
  它**不判基准本身有没有风险**——片子逐字还原了稿子，那就是对得上基准；稿子那句话本身能不能说，是上面那个 skill 的事。

### 方法四件（0.9.0 新增）

**这四件你不会直接用到**——它们不对应任何一站、不读项目材料、不产交付物，由上面的 skill 在该用的时候自己加载。列在这里是为了让你知道它们存在：同一套判断被好几个环节共用时，它只写一份，改一处所有地方跟着改。

- **validating-the-real-problem（验真问题）**——把一句模糊命题或一个表象，验成一句可衡量的真问题并追到根因。读 brief 与复盘共用。
- **elementizing-content（内容要素化）**——把一坨内容拆成能单独打磨、能重新拼装的要素，定位它们，找出短板。拆没跑起来的是找短板；拆已经跑赢的是把还能再用的那几样取走，并把只在那一次成立的（蹭热点、一次性资源、特定档期）单独标出来不要攒。造成片与复盘共用。
- **banking-proven-assets（经验沉淀判准）**——判一批跑出来的东西够不够格留给下一单：有没有证据、过不过得了这一类的线、那个数是不是本项目自己跑出来的、说不说得清它在证明哪段策略。四条缺一不沉。够格的定它沉进哪一格、成色算哪一档（未成文／待验／已验／可放量），并把只有某个人能做的判断追成别人也能照做的规则。**十件全链路 skill 共用。**
- **keeping-metrics-anchored（定性定量对齐）**——每个数字必须说得清它在证明哪段策略，每段策略必须有数在量它。**十件全链路 skill 共用。**

**一条边界值得知道**：沉淀判准判的是"证据上够不够格"，内容要素化判的是"形态上能不能复用"，两道闸不重叠，都要过。
